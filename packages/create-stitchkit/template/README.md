# Application starter

Production-shaped application generated by `create-stitchkit`.

This project describes itself in [`project.json`](project.json) — its
**declaration**: identity, the roles it runs, what it builds, what it needs
before it starts, and the environment variables a deployment must supply.

The declaration is true **with no machine in existence**. A field you cannot
fill in without knowing where the code will run is a *binding*, not a
declaration: ports, hosts, addresses, machine paths and supervision policy are
named there by variable and never by value, and the schema has nowhere to put
them. Change the slug, display name, version or description there and package
names, process names, MCP/OpenAPI identity, UI copy and SEO follow.

Three files are **generated** from it — `ecosystem.config.cjs`,
`ecosystem.dev.config.cjs` and the `env.variables` block of the declaration
itself. Run `bun run gen:declaration` after changing a role; the test suite
refuses a stale copy.

## Start

Point `DATABASE_URL` in `.env` at an existing PostgreSQL database, then run:

```bash
bun run dev
```

The command validates the environment, generates the Prisma client, applies any
database migrations you add and launches:

- Web: <http://localhost:3210>
- UI catalogue: <http://localhost:3210/en/ui>
- API: <http://localhost:3211>
- OpenAPI: <http://localhost:3211/openapi.json>
- MCP: <http://localhost:3211/mcp>

The home page is a compact, domain-free application reference surface.
Add application features as vertical schema → contract → service → client slices.
The exact workflow is in [`docs/ADDING_A_FEATURE.md`](docs/ADDING_A_FEATURE.md),
and root [`AGENTS.md`](AGENTS.md) gives coding agents the application boundaries.

When generated with `--example repository`, one configured GitHub repository
exercises the PostgreSQL cache → contract → typed client →
mutation invalidation → realtime path without adding a demo product domain.
Configure it with `GITHUB_REPOSITORY`; `GITHUB_TOKEN` is optional.
Repository visibility then demonstrates the canonical Prisma enum → shared Zod schema
→ HTTP/UI path without duplicating its allowed values.

**How the browser reaches the API, and what each shape costs.** By default it
does not reach it at all: the browser calls its own origin (`/api/…`), the web
role forwards to the API role (`packages/frontend/src/app/api/[...path]/route.ts`),
and the client is a plain module constant — no address to wait for, no lazy
accessor, nothing to order relative to `<Providers>`. A single-origin deployment
supplies only `INTERNAL_API_URL`.

Two things can pull a deployment out of that, and they are separate questions,
so they have separate variables. **`PUBLIC_REALTIME_ORIGIN`** is the socket: a
WebSocket upgrade does not survive the route handler that forwards `/api`, so
two roles on two ports with nothing in front of them must name the socket's
origin even though their HTTP is already same-origin. Behind one routing layer
that forwards `/socket.io`, leave it unset. **`PUBLIC_API_ORIGIN`** is HTTP, for
a frontend that genuinely dials the API role itself — and setting it changes
nothing on its own: switching is one import in
`packages/frontend/src/lib/api/queries.ts`, documented in
`packages/frontend/src/lib/api/cross-origin.ts`. That variant costs a
server-delivered address, a client built on first use (hence the parentheses),
an ordering requirement relative to `<Providers>`, and `CORS_ORIGIN` on the API
role.

The `/en/ui` catalogue is isolated under
`packages/frontend/src/app/[locale]/ui` and can be removed as one directory;
reusable primitives remain in `components/ui`. It renders the complete
foundation, overlay, data, motion, theme and composition system with generic
fixtures. The root theme uses
`@wrksz/themes/next` with hybrid cookie/localStorage persistence: the server can
read the selected theme, while browser tabs remain synchronized. Client code
imports typed hooks from `@wrksz/themes/client/*`; global theme ownership stays
in the server layout. Interactive changes use a presentation-only runner around
the native View Transition API. Its default is a 250 ms crossfade; the theme
catalogue demonstrates configurable crossfade/radial effects and speeds.
Unsupported browsers and users requesting reduced motion switch immediately.

## Production

Provide a production `.env`, then:

```bash
bun run build
bun run pm2:prod
```

`pm2:prod` is the release: it checks every artifact `build.artifacts` declares,
applies the migrations `release.migrations` declares, and only then starts the
roles from the generated supervision file. There is no separate `db:deploy`
step to remember — the declaration already says the migrations exist, and one
place saying it is the point.

The roles are separate processes and can also be deployed independently.

PostgreSQL is external infrastructure in development and production. The
application owns its schema and migrations; the environment owns the database
process and supplies its connection through `DATABASE_URL`.

Both processes bind `BIND_HOST` (default `127.0.0.1`, loopback only). Set
`BIND_HOST=0.0.0.0` in `.env` to expose the app on every network interface —
that is a conscious opt-in, typically behind a reverse proxy or firewall.

Always drive Prisma through the root `bun run db:*` scripts — invoking the
`prisma` CLI directly fails because the datasource URL is wired through the
`@app/db` package environment, not a static config.

`bun run dev` and `bun run pm2:dev` use the same direct PM2 development path.
