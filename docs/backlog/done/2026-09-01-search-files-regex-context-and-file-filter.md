## Зачем

`search_files` сегодня ищет только литеральную подстроку и возвращает только `path:line`
(`coding-tool-search-patch.ts`). На практике агент после каждого совпадения вынужден звать
`read_file`, чтобы увидеть окружение, — лишний ход и лишние токены на каждый матч.

Референс — поисковый инструмент харнеса, в котором написан этот план; из его ручек ежедневно
несут вес ровно три, и их здесь нет:

1. **regex** — `createServer\(` против буквальной строки; без него ищут дважды и руками;
2. **контекст** — N строк вокруг совпадения в самом результате; закрывает связку
   «search → read» в один вызов;
3. **фильтр по маске** — искать только в `*.ts` или в `packages/core/**`; сегодня режется
   только каталогами exclude-списка.

Не берётся из референса (и почему): режимы вывода count/files-only — достигаются усечением
результата и не окупают схему; сортировка по mtime — недетерминизм в тестах без выигрыша для
модели.

## Результат

- `search_files` принимает `regex?: boolean`, `context?: int` (строки до/после, bounded лимитом
  байт результата), `include?: glob` (тот же компилятор маски, что у `glob` — соседняя таска
  исполняется ПЕРВОЙ, зависимость записана).
- **Regex ограничивается реализуемо, а не обещанием**: у JS `RegExp` в Bun нет таймаута, и
  катастрофический backtracking на одной строке не прерывается ничем in-process — «компиляция с
  таймаут-границей» из первой редакции невыполнима (поймано валидацией). Механизм: (1) отказ на
  конструкции вне линейного подмножества — backreferences и lookaround — typed, с именем
  конструкции; (2) cap длины матчируемой строки; (3) scan-time budget между файлами/строками с
  честным `truncated`. Worker с жёстким `terminate()` — только эскалация, если замер покажет, что
  (1) пропускает реальные паттерны.
- `include` требует файлового предиката в `scanContainedFiles` (сегодня есть только
  `excludeDirectory`) — иначе acceptance по `scannedFiles` недостижим; изменение названо.
- Осознанно отклонено и записано: per-file cap на совпадения (горячий символ съедает бюджет
  строками одного файла) — include-фильтр и context покрывают наблюдённые случаи; defrost —
  живой прогон, где глобальный cap съеден одним файлом.
- Все три опции регистрируются в option-effects-реестре с тестами, переключающими исход.
- Схема остаётся однострочно описуемой; дефолты не меняют сегодняшнего поведения — расширение
  чисто аддитивно.

## Acceptance

- [x] Поиск `createServer\(` с `regex: true` находит то, что литеральный режим не находит;
      обратное тоже проверено.

- [x] `include: "**/*.ts"` сужает объём просканированного — доказано счётчиком `scannedFiles`.

## Что сделано

### Core
- [x] `search_files` принимает `regex`, `context` (строки вокруг совпадения) и `include`
      (та же маска, что у `glob`); дефолты не меняют прежнего поведения.
- [x] **Regex ограничен реализуемо, а не обещанием**: отказ на backreferences и lookaround +
      cap длины строки. «Компиляция с таймаут-границей» из первой редакции невыполнима — у JS
      `RegExp` в Bun нет таймаута, и катастрофический backtracking на одной строке не прерывается
      ничем in-process.
- [x] Результат несёт текст совпавшей строки, поэтому связка «найти и понять» больше не требует
      отдельного `read_file` после каждого матча.

### Что не сделано
- [x] Per-file cap на совпадения отклонён осознанно (горячий символ может съесть общий бюджет);
      defrost — живой прогон, где это случится.
- [x] Файловый предикат в `scanContainedFiles` не понадобился: `include` фильтрует по
      относительному пути уже собранного скана. Ускорение самого обхода — отдельная работа.
