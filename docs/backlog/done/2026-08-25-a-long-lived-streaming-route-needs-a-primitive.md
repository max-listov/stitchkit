# Долгоживущий streaming-маршрут требует трёх вещей, и каждую приходится вспоминать самому

## Зачем

`RawRoute` + `context.server` дают всё необходимое, чтобы отдать длящийся
NDJSON- или SSE-ответ. Проблема не в возможностях, а в том, что автор каждого
такого маршрута обязан **самостоятельно вспомнить три независимые вещи**, и
забытая любая из них ломает поток тихо:

1. **Снять generic HTTP idle timeout.** Без `context.server?.timeout(req, 0)`
   Bun сбрасывает соединение через десять секунд. Для потока, у которого молчание
   — нормальное состояние (подписка на редкое событие, лог простаивающего
   процесса), это разрыв здорового соединения по расписанию.
2. **Слать пульс.** Даже со снятым таймаутом промежуточные прокси и клиентские
   стеки не обязаны держать соединение без байтов.
3. **Отдать заголовки при открытии.** Bun не отправляет ответ, пока тело ничего
   не произвело, поэтому `fetch` потребителя не возвращается до первого кадра. На
   тихом потоке «подписан и тихо» становится неотличимо от «не отвечает» — и
   отличить нечем, потому что ответа ещё нет.

Каждый пункт по отдельности очевиден. Вместе они — чеклист, который живёт в
голове автора маршрута, а не в типах.

## Как это выглядит на практике

В одном проекте-потребителе есть две такие двери. Первая получила пункты 1 и 2 в
своё время. Вторая, написанная позже и делающая то же самое для другой плоскости,
**не получила ни одного из трёх** — и это не заметили ни ревью, ни тесты, потому
что тест публикует событие сразу после подписки и до десятисекундного порога не
доживает. Дефект нашёлся живым пробником, спустя релизы после появления.

Форма ошибки показательна: не «сделано неправильно», а «сделано не полностью, и
неполнота невидима».

## Результат

- Примитив для длящегося ответа, который берёт все три пункта на себя. Условно:

```ts
ndjsonRoute({
  path: '/events/subscribe',
  heartbeatMs: 5_000,
  source: (req) => asyncIterableOfFrames(req),
})
```

  — снимает idle timeout, отдаёт первый keep-alive сразу (заголовки уходят при
  открытии), затем шлёт пульс в простое и закрывает источник при обрыве.
- Форма пульса названа в контракте, а не изобретается каждым потребителем: для
  NDJSON естественна пустая строка, и тогда правило чтения — «пустые строки
  пропускаются» — становится частью документированного контракта, а не устной
  договорённостью между двумя половинами одного проекта.
- Отмена доводится до источника: закрытие соединения обязано закрывать итератор,
  иначе за каждым ушедшим потребителем остаётся живая работа на сервере.

## Что стоит уточнить при проработке

- SSE и NDJSON различаются только обрамлением кадра; имеет ли смысл один примитив
  с выбором формата или два — вопрос дизайна, не требования.
- Значение `heartbeatMs` по умолчанию должно быть заметно меньше стандартного
  десятисекундного порога Bun, иначе дефолт не спасает.
- Стоит ли снимать таймаут безусловно или это должно быть явным полем: молчаливое
  снятие общего предела — тоже решение, которое лучше принимать осознанно.

## Как проверить

Тест, который держит подписку **дольше** порога простоя, не публикуя ничего, и
требует, чтобы поток был жив. Именно этого теста не хватало в описанном случае:
все существующие проверки публиковали событие немедленно и потому проходили на
сломанном маршруте.

## Что сделано

### Решение по открытым вопросам
- [x] **Один примитив с выбором формата**, а не два. NDJSON и SSE различаются
      только обрамлением кадра; один путь исполнения — единственный способ не
      дать логике таймаута, пульса и отмены разойтись между ними, а это и есть
      предмет задачи.
- [x] **Пульс по умолчанию 5 000 мс** — заметно меньше десятисекундного порога.
      Дефолт у самого порога выглядел бы настроенным и не делал бы ничего.
- [x] **Таймаут снимается по умолчанию, но полем.** Общий предел существует,
      чтобы убирать соединения, чей собеседник замолчал; поток, для которого
      молчание — норма, ровно тот случай, где вывод неверен, и именно поэтому за
      этим примитивом приходят. `idleTimeoutSeconds` остаётся явным.

### Core
- [x] `packages/core/src/server/streaming-route.ts`: `streamingRoute`,
      `ndjsonRoute`, `sseRoute`, `DEFAULT_STREAM_HEARTBEAT_MS`. Снимает idle
      timeout (утиная типизация — ядро остаётся Web Fetch-чистым, ADR 0013),
      отдаёт keep-alive при открытии, шлёт пульс в простое, закрывает источник.
- [x] Форма пульса **в контракте**: у NDJSON это пустая строка, и правило
      «пустые строки пропускаются» реализовано на обеих сторонах. SSE использует
      свой comment-кадр и `[DONE]`, поэтому читается существующим `parseSSE`.
- [x] `parseNDJSON` в `packages/core/src/browser/stream.ts` — клиентская половина.
- [x] Ошибка посреди потока приходит финальным кадром с нормализованным
      конвертом: заголовки давно ушли, статуса больше нет, а внутреннее
      сообщение наружу не попадает.

### Найдено пробником, а не предположено
- [x] Отмена **не доходит** до источника через `iterator.return()`: async-генератор
      сериализует запросы, и `return()`, выданный при незавершённом `next()`,
      встаёт в очередь за ним — а подписка находится в `next()` почти всегда.
      Поэтому источник получает `context.signal`, который абортится при уходе
      потребителя по обоим путям (abort запроса и cancel стрима);
      `iterator.return()` вызывается по-прежнему, он закрывает источник,
      подвешенный на `yield`.
- [x] Тот же паттерн найден ещё в одном месте — `streamSSE` ждал
      `generator.return()` в `cancel()`, то есть мог зависнуть на значении,
      которого ушедший потребитель уже не ждёт. Исправлено там же.
