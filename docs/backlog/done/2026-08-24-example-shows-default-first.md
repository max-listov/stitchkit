# Пример показывает дефолт первым, кросс-домен — вариантом

## Зачем

После выноса адреса из байтов пример repository устроен так: браузер набирает публичный origin
api-роли напрямую, поэтому адрес приезжает с сервера при рендере, а клиент и построитель ссылок
собираются при первом использовании — вызовы вида `repositoryApi().read()` вместо
`repositoryApi.read()`, плюс рантайм-ошибка «render inside Providers» при неправильном порядке.

Для честного кросс-доменного случая это единственная корректная форма — механизм верный и должен
остаться. Проблема в распределении: **пример — это то, что копируют.** Сейчас трудный случай лежит
в теле примера, а простой (относительный путь, клиент — константа модуля, никаких скобок) — только
в шаблоне. Человек, взявший пример за основу, унаследует ленивые клиенты и их ошибки, не нуждаясь
в кросс-доменности вовсе.

После hardening-раунда цена видна уже и в декларации: `project.json` примера объявляет
`INTERNAL_API_URL`, `PUBLIC_API_ORIGIN` и `CORS_ORIGIN` обязательными (находка W-1, закрыта
честно — переменные действительно нужны примеру). Скопировавший пример обязывает каждый свой
deployment поставлять три привязки, которые дефолтному одноисточниковому проекту не нужны вовсе.

## Результат

- Тело примера демонстрирует **дефолтную** форму: относительный путь, клиент — константа, вызовы
  без скобок.
- Кросс-доменный случай остаётся в примере **вариантом**: отдельный, явно названный участок
  (файл/раздел) с объяснением, когда он нужен и какова его цена — ленивая сборка клиента, доставка
  origin с сервера, порядок относительно Providers.
- Из текста примера ясно, что скобки — цена кросс-домена, а не новый общий стиль вызова.
- Ни одна возможность не теряется: оба пути работают и покрыты тем же smoke.

### Пример

- [x] Тело примера переведено на дефолтную форму: браузер зовёт свой origin
      (`/api/…`), клиент — константа модуля, вызовы без скобок.
      `packages/create-stitchkit/examples/repository/packages/frontend/src/lib/api/client.ts`,
      `.../lib/api/queries.ts`.
- [x] Пересылку делает web-роль: новый route handler
      `.../src/app/api/[...path]/route.ts`, читающий `INTERNAL_API_URL` в момент
      запроса (`force-dynamic`), поэтому в артефакт ничего не вмораживается.
- [x] Кросс-доменный случай выделен в явно названный файл
      `.../lib/api/cross-origin.ts` (бывший `origin.ts`) с перечисленной ценой:
      адрес приезжает с сервера, клиенты собираются при первом использовании,
      порядок относительно `<Providers>`, `CORS_ORIGIN` на API-роли.
- [x] Цена в декларации снята: `PUBLIC_API_ORIGIN` и `CORS_ORIGIN` снова
      опциональны (`packages/config/src/features.ts`), и порождённый
      `project.json` это говорит. Обязательным остался только
      `INTERNAL_API_URL` — его web-роль разыменовывает на каждый проксируемый
      запрос и каждый серверный рендер.
- [x] Socket.IO без своей переменной подключается к origin страницы — верно за
      маршрутизатором, объединяющим роли. Named в коде и в README.
      **Уточнено следом:** переменная у сокета теперь своя,
      `PUBLIC_REALTIME_ORIGIN`, — см.
      `2026-08-25-each-public-origin-answers-one-question.md`.

### Возражение по коду, которое стоит знать

- [x] «Оба пути зелёные в существующих проверках» выполнено **не полностью, и
      это свойство кода, а не недоработка**. WebSocket-апгрейд не переживает
      route handler, поэтому чисто same-origin realtime требует маршрутизатора
      перед обеими ролями, которого пример поставить не может. В полосе e2e
      браузер идёт дефолтным путём (HTTP через web-origin), а сокет —
      кросс-доменным. Дефолт с realtime без внешнего маршрутизатора не
      существует ни у кого, и делать вид, что существует, было бы хуже.
