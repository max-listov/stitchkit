# Данные, читаемые сборкой, — объявленный вход

## Зачем

Правило границы разделяет две вещи: код и значения места. Есть третья, которая не является ни тем,
ни другим, — **данные, прочитанные во время сборки**.

Случай: страницы, предрендеренные из базы. Такая сборка обязана видеть базу, значит выполнить её
вне целевой машины нельзя. Выносом окружения это **не чинится**: содержимое базы не является
привязкой к месту. Пока категории нет, обещание «один artifact на два deployment'а» либо неверно, либо
молча запрещает целый класс приложений.

Шаблон сегодня этот случай обходит, но нигде не объясняет, что это осознанное решение: страница,
показывающая данные, объявлена динамической, а списки для предрендера статичны. Правило существует
в коде и отсутствует в тексте — значит первый же проект, скопировавший шаблон, его нарушит.

Hardening-раунд подошёл к той же двери с другой стороны и оставил её открытой в трёх местах:
пункт 8 признал, что проверка артефактов ловит только существование, и назвал выбор — «digest,
либо всегда собирать перед bind, либо честно назвать это ручным in-place адаптером»; вопросы 15
и 16 (модель `build(source, inputs) → artifact` из внешнего аудита и контракты
`BuildReceipt`/`DeploymentBindings`) отданы на решение владельца. Третья категория — это и есть
недостающая часть ответа на все три: «inputs» сборки, у которых появляется имя и digest.

## Результат

- В правиле границы появляется **третья категория — данные сборки**. Сборка, читающая данные,
  герметична только если эти данные объявлены и зафиксированы digest'ом.
- Разбор ведётся **по маршруту, а не по проекту целиком**:

  | от чего зависят байты | что законно |
  | --- | --- |
  | только от кода | статика; собирается один раз, переносима |
  | от места (домен, порт) | статикой быть не может — уже решено в S2 |
  | от данных | рантайм-рендер · объявленный снимок с digest'ом · порождение шагом релиза |

- Дефолт для данных — **рантайм-рендер**: сборке база не нужна, страница получает данные там, где
  они живут. Это то, что шаблон уже делает; решение перестаёт быть неявным.
- Объявленный снимок — законная альтернатива для тех, кому нужна статика: сборка читает не живую
  базу, а замороженный экспорт, digest которого становится объявленным входом.
- Порождение на стороне места — тот же release-шаг, что и миграция (выполняется при приведении
  deployment к source); отдельной сущности не заводится.
- Проект, который выбрал сборку с чтением данных и не объявил их, получает отказ гейта — не
  предупреждение.
