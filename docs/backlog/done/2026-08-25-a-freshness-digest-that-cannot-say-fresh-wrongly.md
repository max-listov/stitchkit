# Три хвоста четвёртого аудита

## Зачем

Read-only аудит подтвердил, что прежние blockers закрыты по существу, и назвал
три технических хвоста. Все три проверены чтением и приняты.

1. **Digest мог ложно признать build свежим.** Исключения были заданы *по виду*:
   все `.md`, все test/spec-файлы, любой каталог с именем `generated`. Для
   нынешнего шаблона это верно, но не верно по построению: проект может
   импортировать MDX, а checked-in исходники могут лежать в каталоге, который
   кто-то назвал `generated`. Тогда содержимое меняется, digest — нет, и старый
   artifact объявляется актуальным. Гейт, ошибающийся в сторону «свежий», хуже
   отсутствующего.
2. **Guard базы acceptance не доказывал разделение.** Сравнивался нормализованный
   `hostname:port/database`. Но `localhost` и `127.0.0.1` — один сервер, и два
   DNS-имени одного PostgreSQL тоже. Guard считал их разными базами и разрешал
   разрушающие миграции в базу деплоймента.
3. **Общий бюджет уборки считался стенными часами** (`Date.now()` за
   инъецируемым параметром). Перевод часов назад расширяет тот самый upper
   bound, из которого выведен kill timeout супервизора, а замороженный
   инъецированный clock выдаёт каждому шагу полный бюджет.

Плюс P3 из того же отчёта: сканер манифеста читал только прямые поля секций,
а `overrides` вложены.

## Результат

- Digest исключает только названные вещи: объявленные `build.artifacts`, не-свой
  исходник (`node_modules`, `.git`) и runtime-state.
- Guard решает по имени базы и отказывает независимо от хоста.
- Дедлайн уборки монотонный, и подменить его нельзя.

## Что сделано

### Starter — digest свежести

- [x] `scripts/build-stamp.ts`: исключения выводятся из
      `appDeclaration.build.artifacts` — по пути, а не по имени. Значит
      `packages/db/src/generated` пропускается потому, что декларация называет
      его выходом, а не из-за слова в названии; проект, добавивший artifact,
      покрыт объявлением.
- [x] Исключения «по виду» сняты: `.md` и test-файлы теперь входят в digest.
- [x] `.env*` остаётся снаружи — и это решение, а не недосмотр: binding не вход
      этого build (проект запрещает env-доступ вне границ и собирает packed-lane
      против базы, которая ничего не принимает). Хеширование `.env` отказывало
      бы верному artifact при каждой правке окружения деплоймента.
- [x] Цена записана в комментарии: правка README или теста теперь требует
      пересборки перед релизом — безопасная сторона ошибки.

### Starter — база acceptance

- [x] `scripts/acceptance-database.ts` сравнивает **имя базы** и отказывает
      независимо от хоста; сообщение объясняет, почему хост ничего не
      доказывает, и называет строку для вставки.

### Starter — часы уборки

- [x] `packages/backend/src/cleanup.ts`: `performance.now()`, параметр `now`
      удалён (его никто не передавал), `durationMs` округляется.

### Repo — P3

- [x] `scripts/starter-manifest.ts`: `rangesWithin` обходит секции зависимостей
      рекурсивно, так что вложенный `overrides.<pkg>.stitchkit` тоже пин.

### Регрессия

- [x] `scripts/build-stamp.test.ts`: `.md` роняет свежесть; test-файл роняет;
      каталог, лишь **названный** `generated`, — исходник; объявленный выход
      пропускается; **необъявленный** `.next` НЕ пропускается (фальсификация
      предыдущего теста); `.env` свежести не ломает; декларация действительно
      называет `packages/db/src/generated`.
- [x] `scripts/acceptance-database.test.ts`: то же имя на другом хосте
      отказано; другое имя на том же хосте принято (контроль против правила
      «отказывать всегда»).
- [x] `scripts/starter-manifest.test.ts`: вложенные `overrides`/`resolutions`
      ловятся; пакет, **названный** stitchkit под override, — не диапазон.
- [x] Живой прогон на реальном дереве: после `bun run build` правка `README.md`
      делает artifact несвежим, откат возвращает свежесть; `bun run
      acceptance:local` — EXIT=0.

### Что не сделано

- [x] Подключение к обеим базам для сравнения server identity не делалось:
      это читающее обращение к базе деплоймента из гейта и лишние движущиеся
      части ради случая, который уже закрыт fail-closed правилом по имени.
