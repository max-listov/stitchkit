# Броски до `try` уходят наружу из `dispatch`

## Факт

Два места вызывают консьюмерский код **вне какого-либо `try`**:

- `packages/core/src/server/create.ts:196-197` — `hooks.onRequest(req)`. Первый
  `try` в `dispatch` открывается только на `:256`.
- `packages/core/src/server/create.ts` (внешний хендлер) —
  `customTraceId?.(req)`, то есть `config.traceId`. Вызывается до `dispatch`
  вообще.

Бросок из любого из них **не проходит ни через один слой**: нет
`hooks.onError`, нет конверта ошибки, нет CORS-заголовков, нет строки лога, нет
`x-request-id` на ответе. Наружу уезжает то, что нарисует рантайм — голый 500
без тела в нашем формате.

Это тот же класс дефекта, который 0.28.0 закрыл в логгере (ADR 0039, G3), просто
соседний. Там мы гарантировали «сток не может уронить запрос»; здесь запрос
роняет хук.

## Почему это не теория

Все три наших потребителя пишут в `config.traceId` лямбду, которая **бросает**:

```ts
traceId: () => {
  const traceId = getTraceId();
  if (!traceId) throw new Error('wrapInRequestContext must wrap the stitchkit handler');
  return traceId;
},
```

Один забытый `wrapInRequestContext` в бутстрапе — и приложение отвечает голыми
500 на каждый запрос, без единой строки в логе, объясняющей почему. Сама лямбда
им больше не нужна (с 0.28.0 `traceId: getTraceId` компилируется и фреймворк сам
откатывается), но пока она там — дыра боевая.

## Что сделать

**1. `onRequest` — завести под общий путь ошибок.** Он обязан вести себя как
любой другой выход: `respondError(err)` → `hooks.onError` → конверт → CORS →
строка лога. Технически это расширение `try` так, чтобы `onRequest` попал
внутрь, при том что `respondError` определён выше и уже доступен.

**2. Резолвер `traceId` — не должен мочь убить запрос.** Смысл значения в том,
чтобы пометить строку лога; если резолвер сломался, правильное поведение —
откатиться на `resolveTraceId(req)`, а не потерять ответ. Обернуть вызов в
`try/catch` с тем же фолбэком, что уже стоит на `undefined`.

Вопрос к решению: молчать ли о поломанном резолвере. Склоняюсь к тому, что нет —
один раз сказать в лог стоит, иначе тихо потеряется вся корреляция. Но не на
каждый запрос.

**3. Пройти остальные до-`try` вызовы.** `extractIp`, `resolveSocketIp`,
`corsPreflightResponse` — сейчас фреймворковые и вряд ли бросают, но проверить
стоит заодно, чтобы не возвращаться.

## Что сделано

**Ядро** — `packages/core/src/server/create.ts`

- [x] `hooks.onRequest` заведён под `try` → `respondError(err)`: бросок из гейта
      получает `onError`, конверт проекта, CORS и строку лога. `AppError`
      сохраняет свой статус.
- [x] Резолвер `config.traceId` вынесен в локальный `resolveId(req)`: `undefined`
      и бросок одинаково откатываются на `resolveTraceId`.
- [x] О сломанном резолвере сообщаем **один раз на хендлер** (флаг
      `traceResolverBroken`), не на каждый запрос — открытый вопрос таски решён
      в эту сторону: молчание потеряло бы всю корреляцию без единого слова.
- [x] Заведён общий `warn(line)` — один защищённый путь для всех
      фреймворковых предупреждений. Заменил три разрозненных места
      (затенённые роуты, диагностика output-strip, новый отчёт о резолвере);
      два из них раньше дублировали `if (customLogger) … else console.warn`,
      одно из этих двух было незащищено.

**Проверено, правок не потребовало**

- [x] Остальные до-`try` вызовы: `extractIp`, `resolveSocketIp`,
      `corsPreflightResponse` — фреймворковые, консьюмерского кода не зовут.
- [x] Обработчики raw-роутов уже имеют собственный `try` → `respondError`.

**Тесты** — `packages/core/tests/throws-before-dispatch.test.ts`: бросок гейта
(конверт + CORS + `x-request-id` + одна строка лога), бросок гейта с кастомным

бросающий сток не превращает отчёт в упавший запрос, рабочий резолвер уважается.

**Релиз** — 0.28.1, патч: публичный API не менялся, поменялось только поведение
там, где раньше был необработанный бросок.
