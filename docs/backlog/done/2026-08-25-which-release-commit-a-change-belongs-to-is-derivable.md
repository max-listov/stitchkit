# К какому из двух релизных коммитов относится файл — выводится, но выводится вручную

## Зачем

Релиз двух пакетов из одного дерева упирается в `assert-head`: тег обязан
стоять на голове ветки, значит два тега — минимум два пуша, и раскладку правок
по коммитам надо решить заранее. Это правильное ограничение, оно стоит там
после инцидента с 0.55.0, и трогать его не нужно.

Не записано другое — **как** раскладывать. В этом релизе я выводил её
рассуждением и упёрся в развилку, которую документ не покрывает:
`packages/create-stitchkit/package.json` содержит одновременно правку `files`
(она нужна core-коммиту, иначе его же тест падает на CI) и бамп версии (он
принадлежит стартовому релизу). Один файл — две принадлежности.

Выбранный компромисс: файл целиком уехал в core-коммит, то есть версия стартера
поднялась на коммит раньше своего релиза. Ничего не сломалось — публикует тег,
а не номер в дереве, — но это именно та развилка, которую следующий человек
будет проходить заново и может пройти иначе.

Второе, что стоило времени: каждый пушенный коммит обязан быть тем деревом,
которое прогонялось целиком. Раскладка «core-коммит без starter-правок»
выглядит логично и дала бы красный CI, потому что тесты стартера уже лежали в
core-коммите. Это тоже надо было вывести, а не прочитать.

## Результат

- В `AGENTS.md` записано, как дерево делится на два релизных коммита, включая
  случай файла со смешанной принадлежностью, и почему деление именно такое.
- Записано главное правило, из которого всё остальное следует: **каждый
  запушенный коммит — это дерево, которое прогонялось целиком.**
- Желательно, но не обязательно: раскладка выводится командой, а не глазами.

- [x] Проверить, не решается ли развилка иначе — например, если бамп версии не
      обязан лежать в релизном коммите вообще, а достаточно того, что дерево на
      теге его содержит.

## Что сделано

### Docs
- [x] `AGENTS.md` → «Releasing both packages from one tree». Записано главное
      правило, из которого следует всё остальное: **каждый запушенный коммит —
      это дерево, которое прогонялось целиком**, и явно названа правдоподобная,
      но неверная альтернатива («в коммите только файлы своего пакета»), которая
      даёт core-коммит с падающими собственными тестами.
- [x] Порядок из двух шагов записан: core-коммит первым и со всем, что нужно
      дереву для зелёного (включая правки шаблона, если их читает core-тест),
      затем стартовый.

### Разрешена развилка
- [x] Файл смешанной принадлежности идёт **целиком в более ранний коммит**, и
      это не компромисс: `validateReleaseTag` требует, чтобы версия была *в
      дереве на теге*, а `assertReleaseCommitSubject` — чтобы её называл
      *subject* коммита. Ни то, ни другое не требует, чтобы бамп был **внесён**
      этим коммитом. Публикует тег, а не число в дереве. Пункт плана «проверить,
      не решается ли развилка иначе» закрыт именно этой проверкой кода.

### Не сделано
- [x] Команда, выводящая раскладку автоматически, сознательно не написана — в задаче она
      помечена как желательная, а не обязательная, и правило само по себе
      снимает вопрос. Возвращаться к ней стоит, если следующий двойной релиз
      покажет, что правила недостаточно.
