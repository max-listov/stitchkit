## Зачем

Агент, строящий проект с нуля, почти сразу пишет файл в подкаталог, которого ещё нет:
`packages/shared/src/schemas/currency.ts`. `write_file` в этот момент падает.

Хуже самого падения то, что модель не узнаёт причину. Наружу приходит
`{"error":"INTERNAL_SERVER_ERROR","details":{"message":"Internal server error"}}` — отказ без
объяснения. Модель не может исправить то, чего не видит: в наблюдаемых прогонах после двух таких
ответов она делала ложный вывод, что запись файлов ей недоступна, начинала писать всё в корень, а
затем переставала писать код вовсе и переходила к текстовым отчётам о том, что она «сделала бы».

Тот же класс отказа возникает при попытке перезаписать существующий файл без `overwrite: true`:
поведение задумано, но сообщение о нём до модели не доходит.

## Воспроизведение

```ts
const tools = createAgentCodingTools({ root, authorize: () => true })
const write = tools.find((tool) => tool.name === 'write_file')

await write.handler({ input: { path: 'fresh.md', content: 'x', overwrite: false } })
// ok

await write.handler({ input: { path: 'src/deep/file.ts', content: 'x', overwrite: false } })
// падение: openat: No such file or directory
//   openDirectoryAt → openContainedParent (agent-runtime-coding-tools)

await write.handler({ input: { path: 'existing.md', content: 'x', overwrite: false } })
// падение: openat create: File exists
```

Обе ошибки доходят до модели как `INTERNAL_SERVER_ERROR`; исходный текст остаётся только в логе
хоста. Версия: 0.70.5.

## Результат

- Запись в новый подкаталог работает без предварительного создания каталогов вручную, либо отказ
  прямо называет недостающий каталог и способ его создать.
- Причина отказа доходит до модели: «каталог `src/deep` не существует», «файл существует, передайте
  `overwrite: true`» — вместо `INTERNAL_SERVER_ERROR`.
- Ни один штатный исход `write_file` не выглядит для модели как внутренняя поломка сервера.

## Ресерч 2026-09-01 (по HEAD, репро живьём)

Воспроизведено на Linux против исходников HEAD, прямым вызовом handler:

```
свежий файл        OK {"path":"fresh.md","bytes":1}
новый подкаталог   THROW: Error — ENOENT: no such file or directory, open '/proc/self/fd/12/src'
существующий файл  THROW: Error — EEXIST: file already exists, open '/proc/self/fd/12/fresh.md'
unhandledRejections: 0
```

Механизм невнятности прочитан, а не предположен: `toolResultFromError` → `normalizeError`
(`packages/core/src/tools/execute.ts:172`) вычищает любой не-`AppError` до голого
`INTERNAL_SERVER_ERROR` — по правилу «внутренняя причина не покидает процесс». Оно верно для
consumer-транспортов и слепит модель: ВСЕ штатные отказы coding tools брошены как plain `Error`.
Проходят со смыслом только `conflict()` (stale digest в apply_patch) и FORBIDDEN авторизации —
ровно то, что 0.70.0 уже починил для двух случаев. Этот план доводит до конца тот же ход.

Сырые сообщения ещё и несут путь хоста (`/proc/self/fd/12/src`) — вычистка сейчас единственное,
что мешает утечке; типизированный отказ обязан формулироваться от workspace-relative пути.

Крэш из дополнения на Linux НЕ воспроизводится (0 unhandled) — стек указывает в
`createDarwinFile` (native binding, `contained-files.ts:361`): дефект Darwin-специфичен.
Для него уже существует настоящая macOS CI-полоса (ADR 0135) — регрессионному тесту есть где жить.

## План

- [x] Граница решена в пользу автосоздания: `write_file` создаёт недостающие родительские
      каталоги внутри корня сам. Так ведёт себя каждый мейнстримный харнес (включая тот, в котором
      написан этот план), и наблюдение из «Зачем» показывает, что модели не читают отказ, а делают
      ложный вывод. Реализация — потомковый walk через `mkdirat` по pinned-дескрипторам
      (`openContainedParent` расширяется режимом `create`), симлинк в цепочке по-прежнему отказ.
      Альтернатива «named refusal + явный шаг» отклонена: лишний ход на каждый новый каталог и
      доказанное непонимание отказов моделями.
- [x] **Порядок: authorize раньше любой мутации.** Сегодня `openContainedParent` вызывается ДО
      `authorizeCodingTool` (`coding-tool-files.ts:97→99`); create-режим внутри walk означал бы
      создание каталогов неавторизованным вызовом. Недостающие сегменты вычисляются walk'ом,
      authorize получает их списком в payload операции `write` (`createsDirectories`), создание —
      только после разрешения.
- [x] **Darwin — самая дорогая часть, и она названа**: у native binding нет `mkdirAt` —
      новый метод, пересборка обеих `darwin-{arm64,x64}.node`, доказательство только в
      real-Darwin CI-lane (ADR 0135). На Linux — `mkdir` через `descriptorPath` + повторный
      `openDirectoryAt` с `O_NOFOLLOW`: подмена сегмента симлинком между mkdir и open fails
      closed, EEXIST от гонки двух писателей толерируется с перепроверкой `isDirectory()`.
- [x] **Выход называет созданное**: `createdDirectories: string[]` в `FileWriteOutputSchema`.
      Авто-создание само вносит новый риск — опечатка в пути перестаёт быть ошибкой и становится
      молчаливым успехом не туда; «создан новый top-level каталог `packags`» — единственный
      tripwire, по которому модель ловит свою опечатку.
- [x] Типизировать штатные отказы `write_file`: «файл существует — передай overwrite: true» →
      `conflict()`; «родительский каталог отсутствует» исчезает как исход (автосоздание), а если
      сегмент занят файлом или симлинком — `conflict()` с workspace-relative именем сегмента.
      Сообщения формулируются ТОЛЬКО от relative-пути; хостовые `/proc/self/fd/…` не покидают
      процесс, как и сейчас.
- [x] Проверить остальные операции того же набора на этот класс: штатный исход не должен приходить
      как внутренняя ошибка.
- [x] Тесты: запись в новый подкаталог, запись поверх существующего файла с флагом и без, выход за
      корень остаётся запрещённым.

## Дополнение 2026-09-01: отказ не только невнятен, он роняет процесс-хост

Замер того же дня показал, что это не только вопрос формулировки. Ошибка выбрасывается из
асинхронного колбэка вне цепочки промиса и доходит до процесса как необработанная:

```
[stitchkit] unhandled error: 219 |  fchmod(descriptor, mode & 4095, (error) => error ? reject(error) : resolve());
error: openat create: File exists
    at createDarwinFile (index-1z5xxfst.js:224:30)
    at writeContainedFile (index-1z5xxfst.js:247:13)
    at <anonymous> (agent-runtime-coding-tools.js:306:17)
    at async runToolMethod (index-qm87g51s.js:314:29)
```

Хост-процесс от этого умирает. В наблюдаемом прогоне девять агентов работали в одном процессе: одна
неудачная запись файла у одного из них обрывала ходы всех остальных, супервизор поднимал процесс
заново, и цикл повторялся. Один неудачный вызов стоил работы восьми участникам.

Хост обязан переживать отказ инструмента, и на стороне потребителя это уже закрыто. Но отказ
штатной операции не должен покидать цепочку промиса вызова: `toolResultFromError` его не видит,
и `onToolError` тоже.

- [x] Отказ записи возвращается вызывающему как результат инструмента, а не как необработанная
      ошибка процесса. **Корень честно помечен невыясненным**: на HEAD `createDarwinFile` читается
      полностью обёрнутым в promise-цепочку, стек дополнения снят с dist 0.70.x — механизм
      выясняется на Darwin, а не постулируется по строке бандла.
- [x] Тест: неудачная запись при смонтированных инструментах не порождает необработанного
      отклонения — живёт в real-Darwin CI-lane (ADR 0135), на Linux дефект не воспроизводится
      (замерено: 0 unhandled).
- [x] Auto-mkdir отказывается вести цепочку через сегмент-файл и сегмент-симлинк — typed, с
      именем сегмента; это новое поведение, и ловит его только новый тест.
