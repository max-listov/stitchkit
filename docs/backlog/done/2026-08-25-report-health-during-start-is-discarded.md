# reportHealth, вызванный внутри start, затирается безусловным healthy

## Зачем

`ManagedResourceContext.reportHealth` внутри `start` — это no-op. После успешного возврата старта
ядро делает (`packages/core/src/application/kernel.ts`, ветка перехода в `ready`):

```js
record.state = "ready";
record.health = "healthy";
publish();
```

безусловно, независимо от того, что ресурс сообщил секундой раньше.

Заметить это трудно ровно потому, что минимальный пример в гайде сообщает `healthy`:

```ts
start: async ({ signal, reportHealth }) => {
  await db.connect({ signal })
  reportHealth('healthy')
},
```

Значение совпадает с затирающим, поэтому пример «работает», и читатель уносит из него, что
сообщать здоровье из `start` — нормальный способ. Для ресурса, который стартует **деградировавшим**,
это молча неверно: сообщение отбрасывается, и снаружи ресурс выглядит здоровым.

Случай не редкий: ресурс, который поднялся, но ещё не получил ответа от внешней стороны —
подключение, которое дозванивается в фоне, — честно стартует деградировавшим. Сегодня он обязан
докладывать здоровье **после** `app.start()`, то есть держать `reportHealth` из контекста в
переменной, переживающей старт. Это работает, но противоречит и форме API, и примеру.

## Воспроизведение

```ts
const app = createApplication({
  id: 'repro',
  resources: [
    defineManagedResource({
      id: 'slow',
      start: ({ reportHealth }) => { reportHealth('degraded'); },
    }),
  ],
});
const snapshot = await app.start();
console.log(snapshot.health); // 'healthy' — сообщённое 'degraded' потеряно
```

## Результат

Одно из двух, и выбор — ваш:

- либо `start` перестаёт затирать уже сообщённое здоровье и присваивает `healthy` только тогда,
  когда ресурс ничего не сообщил;
- либо гайд прямо говорит, что `reportHealth` внутри `start` не сохраняется, убирает вызов из
  минимального примера и показывает, где его делать вместо этого.

Первое лучше: сейчас API принимает значение и молча его выбрасывает, а это худший вид отказа —
без ошибки и без следа.

## Заодно стоит проверить

`isReady()` требует, чтобы каждый **required** ресурс был `healthy`, поэтому «готов, но
деградировал» для required недостижимо by construction. Это, похоже, намеренно и согласуется с
фразой гайда про optional — но в гайде это нигде не сказано прямо, а различие заметное: потребитель,
который ожидал «lifecycle ready + health degraded», получает `ready: false` и не понимает, почему.
Одно предложение в разделе Readiness and health закрыло бы вопрос.

## Что сделано

### Выбран первый вариант
- [x] `start` больше не затирает сообщённое здоровье: `healthy` присваивается
      только ресурсу, который **ничего не сообщил**. API, принимающий значение и
      молча его выбрасывающий, — худшая форма отказа, и это решающий довод.

### Последствия, вскрытые правкой, а не описанные в отчёте
- [x] Проверка активации сравнивала `health !== 'healthy'`, что означало
      «потерял готовность» лишь пока старт присваивал `healthy` безусловно.
      Честно стартовавший деградировавшим ресурс спотыкался о проверку про
      потерю того, чего у него не было.
- [x] **Первая попытка чинить это ослаблением проверки была неверной** — её
      поймал валидатор. Ложной зелени не возникало (финальный гейт готовности
      всё равно отказывал), но пропадала атрибуция: `onResourceFailure` молчал,
      фаза не попадала в `failures`, и все нижележащие `activate` успевали
      отработать — расписания вооружались, long poll открывались — до отката.
      Проверка возвращена; ветвится только **формулировка**.
- [x] Дискриминатор — не «сообщал ли» и не «каким было здоровье до активации»:
      оба верны и для базы, которая упала, и для ресурса, стартовавшего
      деградировавшим. Введён `everHealthy` — «был ли здоров хоть раз». Ресурсу,
      который никогда не был здоров, советуют `required: false`; тому, который
      был и перестал, — читать `onResourceFailure`. Совет «сделай необязательным»
      для только что упавшей базы — худшее, что можно предложить.

### Docs
- [x] `docs/guide/application-kernel.md`: сказано, что `reportHealth` из `start`
      сохраняется; что **`required` по умолчанию `true`** (нигде не было
      сказано, а без этого весь совет не читается); что готовность требует
      здоровья всех required, поэтому «ready + degraded» для required
      недостижимо; и что optional-ресурс не гейтит готовность, но **двигает
      агрегат** приложения в `degraded` — это может перевернуть readiness-пробу.
- [x] `CHANGELOG.md` и `docs/guide/upgrading.md`: миграция называет **оба**
      случая. Ранняя пессимистичная `'unhealthy'`, которую старое затирание
      чинило, требует противоположного лекарства — сообщить выздоровление, а не
      прятать ресурс за `required: false`. Инструкция «грепни все `reportHealth`
      в `start`, а не только degraded».
