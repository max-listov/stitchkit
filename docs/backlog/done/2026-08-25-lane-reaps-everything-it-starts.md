# Полоса убирает всё, что подняла, — даже умирая

## Зачем

Воспроизведённый инцидент на разделяемом dev-хосте (2026-08-24, вечер UTC), снятый живьём:

- **101 осиротевший процесс** с cwd `/tmp/stitchkit-starter-lane-*/... (deleted)`:
  47 × `bun dist/index.js` (api-роль), 27 × `next-server` (web-роль), остальное — обвязка.
  Старейший — 15:55 UTC, накопление ~2.5 часа непрерывных прогонов.
- Суммарно **4.3 GiB RSS** плюс размазанный swap. Хост: swap 15/15 GiB исчерпан, load 44 на
  12 CPU, 4339 процессов в системе, **4 OOM-kill** — включая невиновных: systemd-юнит и два
  playwright chrome-headless. Хост переставал отвечать; чужие проекты на нём мигали.
- После точечного SIGTERM всех сирот (умерли мягко — их никто просто не звал): load 44→15,
  available RAM 4→8.6 GiB.

Механика знакома по собственным находкам S4/S6: **смерть обвязки не убивает роли**. Полоса
поднимает роли, затем умирает не по счастливому пути (падение проверки, таймаут, OOM, interrupt
агента) — cleanup не выполняется, каталог позже удаляется, роли живут с deleted-cwd и копятся с
каждым прогоном. Тот самый класс «убитый лаунчер, живая роль», от которого шаблон уже защищён, —
но применённый к самой полосе.

## Результат

- Полоса **владеет группой процессов**, а не списком PID: всё поднятое стартует в собственной
  process group / сессии, и уборка — `kill` по группе в `finally`/trap, а не перечисление детей.
- Уборка выполняется **на любом исходе**: зелёный, красный, таймаут, сигнал самой полосе.
- **Следующий прогон подметает предыдущий**: перед стартом полоса находит и снимает процессы
  с cwd в несуществующих каталогах своего префикса — сироты не переживают один запуск.
- Полоса fail-closed: не смогла убрать поднятое — это её падение с внятной ошибкой, а не
  предупреждение.
- Регрессия: убить обвязку полосы посреди прогона — через N секунд не остаётся ни одного
  процесса из её каталога.

## Что сделано

Находка подтверждена на моей стороне до правки: сразу после последнего прогона
на хосте висели **три** процесса с cwd
`/tmp/stitchkit-starter-lane-i9RVww/generated-repository/... (deleted)` — две
web-роли и одна api. Механика ровно та, что описана: `bun run start:api` — это
лаунчер, роль живёт за ним, и `child.kill('SIGTERM')` до неё не доходит.

### Общий модуль

- [x] `scripts/lane-processes.ts` — владение группой, а не списком PID:
      `stopProcessGroup()` шлёт сигнал по отрицательному pid, поэтому достаёт и
      лаунчер, и роль за ним, и всё, что они успели породить.
- [x] `sweepAbandonedLaneProcesses()` — подметание перед стартом: находит
      процессы, чей cwd лежит в **удалённом** каталоге с lane-префиксом, и
      снимает их сначала SIGTERM (все замеренные сироты умирают мягко — их
      просто никто не звал), затем SIGKILL уцелевших. Живой соседний прогон не
      затрагивается: условие `(deleted)` обязательно, иначе фикс сам стал бы
      следующим инцидентом.
- [x] Отдельно ловится supervisor-демон: у supervised-полосы `PM2_HOME` в своём
      временном каталоге, поэтому её демон не виден по cwd, зато виден по
      `PM2_HOME=` в `/proc/<pid>/environ`, указывающему на несуществующий
      каталог. Демон Макса (`PM2_HOME=/root/.pm2`) под условие не попадает.
- [x] `reapOnTermination()` — уборка на сигнал самой полосе. `finally` покрывает
      бросок и только его; прерванный прогон — как раз тот, что оставляет
      больше всего.
- [x] `assertNothingSurvives()` — fail-closed: полоса падает с перечислением
      pid'ов, если после уборки в её каталоге кто-то остался. Предупреждение
      здесь читалось бы как шум, а «наверное, ничего страшного» — это и есть то,
      во что превратились два с половиной часа прогонов.

### Полосы

- [x] `scripts/starter-lane.ts`: роли поднимаются `detached: true` (лидеры
      группы), подметание перед стартом, уборка в `finally` и на сигнал,
      fail-closed в конце.
- [x] `scripts/supervised-lane.ts`: то же плюс гашение своего pm2-демона
      (`delete all`, затем `kill`, `save` — никогда) на любом исходе, включая
      сигнал.
- [x] `packages/create-stitchkit/template/scripts/supervision-signal.test.ts`
      тоже тёк — по одной роли за прогон, и именно в негативном случае, где
      роль сигнала не видит по построению. Теперь группа добивается после
      измерения.

### Регрессия

- [x] `scripts/lane-processes.test.ts` — четыре случая, каждый на живых
      процессах: убийство группы достаёт роль за лаунчером; SIGKILL обвязки

      роль, и её снимает подметание следующего прогона; сигнал самой полосе
      убирает поднятое; выживший в каталоге — это падение, а не предупреждение.
