# CIMD cache correctness

## Зачем

Два дефекта корректности на одном пути, оба открываются **обычными**, а не
враждебными заголовками.

**1. `Age` ломает положительный кэш через NaN.** `tools/oauth-provider.ts:302-308`
считает `Number(headers.get('age') ?? 0)`; нечисловое значение даёт `NaN`, дальше
`freshnessMs: NaN` → `expiresAt: NaN` → попадания не будет никогда, при этом запись
всё равно кладётся в кэш и занимает слот LRU:

```
max-age=600                  -> 1 фетч  / 5 авторизаций
max-age=600 + Age: junk      -> 5 фетчей / 5 авторизаций
max-age=600 + Age: "10, 20"  -> 5 фетчей / 5 авторизаций
```

`Age: 10, 20` — это то, что отдаёт `Headers`, когда два прокси дописали по одному
значению. То есть срабатывает на нормальном документе за CDN. Отдельно:
`Age: -1000000` молча поднимает свежесть до часового потолка `maxTtl`.

**2. `no-store` со стороны origin отключает отрицательный кэш.**
`oauth-provider.ts:405,409,461`: `cacheFailure` инициализируется `true` (правильно,
fail-closed), а затем перезаписывается значением `freshness.store`, смешивая «стоит
ли кэшировать **успех**» и «стоит ли кэшировать **отказ**».

```
некорректный документ, без cache-заголовков -> 1 фетч  / 5 авторизаций
некорректный документ + no-store            -> 5 фетчей / 5 авторизаций
```

Политика отрицательного кэша принадлежит нам, а не документу: `no-store` говорит,
что не надо хранить **его содержимое**, и ничего не говорит о том, как долго мы
имеем право помнить, что документ невалиден.

## Результат

- Нечисловой, множественный или отрицательный `Age` не отключает кэширование.
- Запись с невалидной вычисленной свежестью в кэш не попадает и слот не занимает.
- Отрицательный кэш живёт по собственной политике и не управляется заголовками
  origin.

  hardening-задача.
- Сам факт неаутентифицированного разрешения CIMD дефектом не считается: это
  часть протокола.

  файла 21 строка, из них две про `allowedHosts` и одна про `approvedScopes`.

**Осталось неверным по замерам (счёт фетчей на 5 авторизаций).**

- `Age` принимается только как голое целое: `10, 20` (нормальный вывод двух прокси),
  `1.5`, `-5`, `abc` дают `age = 0`. `Expires +1h` с `Age: 1800` даёт 1 799 484 мс,
  а с `Age: 1800, 5` — 3 599 484 мс: **лишние полчаса устаревания идентичности клиента**.
- Неразбираемая свежесть падает в **пятиминутный дефолт**, а не в «просрочено»:
  `max-age=abc`, `max-age=-5`, `Expires: not-a-date` → 300 000 мс. RFC 9111 §5.3
  требует считать неразбираемый `Expires` уже истёкшим.

### Осталось сделать

- [x] `Age` разбирается по RFC 9111: `parseAgeSeconds` берёт первое значение

- [x] Неразбираемые `max-age` и `Expires` дают `freshnessMs: 0` («уже просрочено»,
