# Hardening round по итогам аудита декларации и placement-контура

## Зачем

Внешний read-only аудит прошёл по всему staged-дереву итерации. Его вердикт по
существу: направление верное, но **дерево обещает больше, чем гарантирует код**.
Это точный диагноз, и он попадает в то место, которое я сам защищал сильнее
всего — в утверждение «граница держится формой, а не ревью».

Каждая находка ниже **воспроизведена мной лично**, а не принята на слово.
Результаты пробников приведены рядом. Находки, которые я проверить не смог или с
которыми не согласен, вынесены в отдельные разделы в конце — они не молчат.

Пока эта таска не закрыта, релиз стоит.

## Блокеры

### 1. Схема молча съедает неизвестные поля

`ProjectDeclarationSchema` и все вложенные объекты не `.strict()`, поэтому Zod
по умолчанию **отбрасывает** незнакомые ключи. Проверено:

```
unknown top-level keys (deployTo, supervisor) -> SILENTLY DROPPED
typo `listner` внутри роли                     -> SILENTLY DROPPED
```

Второй случай особенно плох: опечатка в имени **необязательного** ключа
превращает роль со слушателем в роль без слушателя, и декларация остаётся
валидной. Fail-closed сейчас работает только для незнакомой *версии* схемы, а не
для неправильной декларации знакомой версии — при том, что ADR 0104 и changelog
обещают именно fail-closed поведение читателя.

- [x] Сделать декларацию и все вложенные contract-объекты строгими.
- [x] Записать политику неизвестных ключей явно: это часть контракта, а не
      деталь Zod.
- [x] Регрессия на опечатку в имени необязательного поля и на лишний ключ
      верхнего уровня при знакомой `schemaVersion`.

### 2. «Enforced by shape» — сильнее, чем реализация

Комментарий схемы, ADR и changelog утверждают, что в декларации негде разместить
порт, хост, абсолютный путь или другое значение места. Проверено — есть где:

```
artifact "..\outside\dist"                        -> ACCEPTED
artifact "C:\srv\app"                             -> ACCEPTED
build.command "curl http://api.internal | sh"     -> ACCEPTED
role command "bun a.ts --port 3210"               -> ACCEPTED
role command "node /srv/app/index.js"             -> ACCEPTED
```

Причины конкретные: `RepositoryPathSchema` смотрит только на `/` и потому не
видит backslash-traversal и Windows-пути; проверка на `://` применяется к
командам ролей и **не применяется к `build.command`**; а сами команды —
произвольные строки, куда помещается что угодно.

- [x] Закрыть backslash и Windows-пути в `RepositoryPathSchema`.
- [x] Распространить проверку абсолютного адреса на `build.command`.
- [x] И — главное — привести **утверждение** в соответствие с проверкой. Либо
      формализовать форму (см. пункт 3, он это почти решает), либо честно
      ослабить формулировку до «в схеме нет специальных полей для значений
      места». Оставлять текущую формулировку нельзя: это ровно тот класс
      дефекта, который эта итерация и вычищала.

### 3. Команды должны быть argv, а не строка для shell

`scripts/declaration.ts` разбирает команду через `role.commands[mode].split(' ')`
и потом вставляет части в порождаемый JS вручную как `'${part}'`. Это ломается на
кавычках, экранированных пробелах и путях с пробелами, и одновременно даёт
классическую проблему экранирования при генерации кода.

Правильная форма:

```json
"commands": {
  "production": { "executable": "bun", "args": ["scripts/serve.ts", "production"] }
}
```

Она заодно **закрывает пункт 2 по-настоящему**: у argv нет места для shell-строки,
а `executable` и элементы `args` можно валидировать по отдельности. И генерация
идёт через `JSON.stringify`, а не через ручные кавычки.

- [x] Перевести `ProjectRoleSchema.commands` на `{ executable, args }`.
- [x] Генератор сериализует argv через `JSON.stringify`, включая
      `workingDirectory`.
- [x] Регрессия: packages/create-stitchkit/template/scripts/declaration.test.ts::a space and a quote reach the supervision file unmangled

### 4. Бюджет остановки не замкнут

Бэкенд берёт `gracePeriodMs` из декларации (15 000). Сервер добавляет
`forceTimeoutMs` со значением по умолчанию **5 000** (проверено:
`packages/core/src/server/shutdown.ts:16`). PM2 убивает через 20 000.

```
15 000 grace + 5 000 force = 20 000 = kill_timeout
```

Запаса нет вообще — ни на jitter таймеров, ни на `onComplete`, где ещё
выполняются `mcp.close()` и `prisma.$disconnect()`. При этом
`assertSupervisionAllowsDrain` сверяет только `killTimeout >= drainFloor`, то
есть проверяет треть бюджета и рапортует, что супервизор «allows the full
shutdown».

- [x] Проверять полный минимальный бюджет завершения, а не только пол слива.
- [x] Решить, различает ли декларация *clean-drain floor* и *total termination
      floor*, и записать выбор.
- [x] Регрессия на арифметику: бюджет, впритык равный kill timeout, отвергается.

### 5. Forwarded origin не имеет границы доверия

`request-origin.ts` безусловно доверяет `x-forwarded-host`, затем `Host`, и берёт
`x-forwarded-proto` без проверки. Это значит, что **внешний заголовок задаёт
canonical URL, sitemap, robots и OG-метаданные**. Ограниченный LRU защищает
память, но не корректность выдачи.

Горькая деталь: мой же multi-origin smoke, которым я доказывал переносимость,
одновременно демонстрирует и подмену origin — я смотрел на него как на
доказательство и не увидел вторую половину.

- [x] Валидировать схему: только `http` и `https`.
- [x] Определить контракт доверенного прокси: либо allowlist хостов, либо
      обязательный `PUBLIC_WEB_ORIGIN` в production, либо явное согласие
      доверять forwarded-заголовкам.
- [x] Незаявленный `x-forwarded-host` отвергается — проверяет
      `assertArtifactIsPlacementFree` в `scripts/web-surface-smoke.ts`, то есть
      packed-полоса на живой роли, а не unit-тест.
- [x] Smoke переносимости переписать так, чтобы он доказывал переносимость **в
      рамках разрешённой политики**, а не «любой заголовок принимается».

## Обязательно, но не блокирует запуск

### 6. Placement policy всё ещё лежит в репозитории — и acceptance это отрицает

`LOCAL_SUPERVISION` в `scripts/declaration.ts` фиксирует `restart: true` и
`killTimeoutMs: 20_000`. Это политика места. Плюс `BIND_HOST` имеет
repository-default `127.0.0.1`.

Поэтому acceptance зонтичной задачи — «ни один файл репозитория не содержит
значения, различающегося между deployment'ами» — **фактически неверен**. Аудит прав.

Моя позиция по частям расходится: loopback-дефолт `BIND_HOST` я считаю
осознанным *safety*-дефолтом кода (выставление наружу должно быть явным
согласием), а не протёкшим значением места, и удалять его не предлагаю. А вот
`kill_timeout` и `restart` — именно политика места, и она в репозитории есть.

- [x] Честно разделить в тексте и в структуре: **переносимая декларация** и
      **локальный placement-адаптер** для ручного пути.
- [x] Исправить acceptance зонтичной задачи на то, что действительно верно.
- [x] Решить и записать, допустимы ли safe-дефолты у bindings (случай
      `BIND_HOST`) — сейчас он одновременно называется binding и имеет дефолт.

### 7. `dotenv override: true` в production-супервизии

Порождённый `ecosystem.config.cjs` вызывает dotenv с `override: true`. Значит
`.env` из репозитория **перебивает окружение, которое впрыснул deployment**. Для
bindings приоритет обязан быть обратным: внешнее окружение выигрывает.

- [x] Убрать `override` из production-контура либо обосновать обратный приоритет.
- [x] Регрессия на приоритет: впрыснутая переменная не перекрывается файлом.

### 8. Проверка артефактов проверяет только существование

`assertBuildArtifacts` смотрит, что путь есть. Старый `dist`, `.next` или
Prisma-клиент от другого снимка исходников пройдут проверку. Release-скрипт не
знает, когда они собраны, из чего и одним ли билдом.

Отдельно: миграции объявляют `root` **и** `lockfile`, а проверяется только
`root` (проверено — в `release-steps.ts` `lockfile` не упоминается вне
комментария).

- [x] Как минимум: проверять и `lockfile`.
- [x] И либо ввести artifact/source digest, либо всегда собирать перед bind,
      либо **назвать вещи своими именами** — это пока ручной in-place адаптер, а
      не завершённый artifact pipeline. Третий вариант дешевле и честнее; выбор
      зависит от решения по модели (см. «Требует решения»).

### 9. `onResourceFailure` не покрывает все фазы и не переживает async-наблюдателя

Проверено: в `application/kernel.ts` восемь вызовов `reportFailure` против
четырнадцати `catch`-блоков. Changelog утверждает, что причину сообщает **каждый**
сбой фазы. Кроме того, колбэк объявлен как `(failure) => void`: TypeScript
пропустит `async`-наблюдателя, а его отклонённый промис никто не поймает —
синхронный `try/catch` вокруг вызова его не видит.

Тест с именем *every failing phase* проверяет `seen.length > 0` — это не «every».

- [x] Пройти каждый `catch` и решить по каждому: сообщает или намеренно нет.
- [x] Сигнатура `void | Promise<void>` с изоляцией отклонения.
- [x] Тест-таблица всех фаз с точной ожидаемой причиной, вместо счётчика.

### 10. Контракт `runtime.close()` внутренне противоречив

Гид (`docs/guide/agent-runtime.md:221-224`) утверждает одновременно три вещи:
«every combination is bounded», «omit `forceTimeoutMs` and it waits for
settlement» и «`close()` never returns while a run is still in flight». Без force
timeout ожидание не ограничено; с ним — возврат возможен при живом прогоне.
Три утверждения не выполняются вместе.

- [x] Выбрать один честный контракт и привести код и текст к нему. Лучший
      вариант — structured result (`settled` / `timedOut` / `remaining`): он
      описывает то, что происходит, вместо обещания, которого не бывает.

### 11. `shift()` называется ring

`observability.ts` держит `emittedOrder: string[]` и вытесняет через `shift()`.
Память ограничена — это правда и это было целью. Но комментарий называет это
ring, а после заполнения окна каждое вытеснение сдвигает массив: горячий путь
становится O(window), а не O(1).

- [x] Настоящий кольцевой буфер или deque, либо снять слово «ring» из кода и
      таски.

### 12. `env.required` содержит `required: false`

Секция называется «required», а половина записей в ней — необязательные. Имя
противоречит содержимому. Схема ещё не опубликована, переименование бесплатно.

Отдельно: `boolean` из JSON Schema намеренно отображается в `'string'`
(`declaration.ts:43`). Это неверное описание типа.

- [x] Переименовать в `env.variables` (или `env.bindings`).
- [x] Либо добавить форму `boolean`, либо fail-closed на неподдерживаемой форме —
      но не описывать её неправильно.

## Требует решения Макса, а не моего

### 15. `commit` в модели: убрать или оставить

Аудит предлагает заменить модель на:

```
build(source snapshot, build inputs) → immutable artifact
bind(artifact, deployment bindings)  → deployment
```

с аргументом, что artifact обязан существовать без коммита: dirty tree, tarball,
CI workspace — все они законные источники, а commit это в лучшем случае
provenance, а не предусловие.

**Я с аргументом согласен по существу**, и менять словарь в одностороннем
порядке было нельзя: он пришёл со стороны платформы, и вся терминология —
`RepositoryPathSchema`, ADR 0104, тексты тасок — построена на нём.

**Решение принято владельцем: модель аудита взята целиком.** Действующие
термины — source · build · artifact · bind · binding · deployment; `commit`
означает только git-коммит и словарным термином не является, `stand` не
существует. Идентичность у source есть всегда: незакоммиченное дерево
выкатывается запечатанным снапшотом.

- [x] Решение Макса получено и применено к текстам волны —
      `docs/backlog/done/2026-08-25-declaration-wave-follow-up.md`.

### 16. `BuildReceipt` и `DeploymentBindings` как контракты ядра

Аудит предлагает ядру дать ещё два generic-контракта помимо
`ProjectDeclaration`. Это расширение области ответственности фреймворка, а не
hardening. Считаю, что это отдельное решение с отдельным ADR, и в этот раунд оно
входить не должно.

**Решение владельца: нет, вопрос закрыт.** Это словарь стороны места, а не
фреймворка; обязательные контракты об этом в ядре сделали бы шов ненейтральным.
Вернуться можно при появлении второго реального читателя формата.

- [x] Решение Макса получено: контрактов в ядре не заводим —
      `docs/backlog/done/2026-08-25-declaration-wave-follow-up.md`.

## С чем не согласен

**«Fail-closed не работает для опечатки `drainFloorMS`».** Конкретно этот пример
неверен: `drainFloorMs` обязателен, поэтому опечатка в **обязательном** поле
падает на отсутствии поля. Проблема реальная, но проходит через
**необязательные** ключи (`listner` вместо `listener`) — я это воспроизвёл, и
пункт 1 написан по воспроизведённому случаю, а не по приведённому.

**Оценка «соответствие invariants 6/10».** Спорить с числом не буду, но замечу,
что четыре из пяти блокеров — это расхождение между *текстом* и *кодом*, а не
неработающий код. Механика в основном делает то, что должна; переоценены
формулировки. Это дешевле чинить и опаснее оставлять.

## Пересечения с моими валидаторами

Три собственных read-only валидатора запущены параллельно с этим аудитом

## Валидатор 1 из 3 — границы и публичная поверхность

Первый из моих собственных read-only валидаторов вернулся. **Каждая находка ниже
воспроизведена мной лично**; результаты пробников приведены. Пересечения с
внешним аудитом отмечены как подтверждённые дважды.

### Подтверждено дважды — приоритет

Эти находки независимо нашли и внешний аудит, и мой валидатор. Они уже описаны
выше и приоритетнее остальных:

| Что | Внешний аудит | Валидатор |
| --- | --- | --- |
| Схема нестрогая, неизвестные ключи молча съедаются | 1 | V-3 |
| «Enforced by shape» сильнее реализации | 2 | V-1, V-2, V-5, V-6, V-7 |
| `build.command` не покрыт проверкой адреса | 2 | V-2 |
| `RepositoryPathSchema` не видит Windows и backslash | 2 | V-6 |
| Команда как shell-строка вместо argv | 3 | V-23 |
| `env.required` содержит `required: false` | S7 | V-12 |
| `boolean` отображается в `'string'` | S7 | V-23 |
| Inbox-таска adoption устарела на момент написания | S1 | V-16 |

Валидатор при этом нашёл в границе **больше дыр**, чем аудит. Дополнительно к
уже описанным (проверено):

```
readinessPath "//evil.example.com/health"                   -> ACCEPTED
migrations.engine "postgres://u:p@10.0.0.5:5432/db"          -> ACCEPTED
role command "API_TOKEN=sk-live-abc bun dist/index.js"       -> ACCEPTED
role command "bun dist/index.js --db db.internal:5432"       -> ACCEPTED
```

То есть в декларацию помещается не только порт и путь, но и **строка
подключения с учётными данными** и **секрет** — ровно те два пункта запрета,
которые я перечислял в шапке схемы. Пункт 2 расширяется: проверять надо не
`://`, а один предикат «называет машину» — схему, `//host`, ведущий `/` или `~`,
букву диска, `host:port` и голый IPv4 — и применять его ко **всем** четырём
свободным строковым полям: `role.commands`, `build.command`, `migrations.engine`,

## Валидатор 2 из 3 — корректность и правдивость утверждений

Второй валидатор целенаправленно исключил всё, что уже записано выше, и вернул

### Новый блокер: декларация примера недообъявляет то, что примеру нужно

**W-1.** Это самая тяжёлая находка всего раунда, потому что она даёт **сломанный
работающий deployment**, а не неверную фразу. Проверено:

```
examples/repository/project.json:
  INTERNAL_API_URL  -> required: false
  PUBLIC_API_ORIGIN -> required: false
  CORS_ORIGIN       -> required: false
```

При этом `examples/repository/.../lib/api/place.ts` **бросает**, если их нет, а
`providers/index.tsx:15` вызывает `publicApiOrigin()` на каждом рендере — то есть
на каждой странице, потому что `Providers` оборачивает весь layout.

Сторона места, читающая эту декларацию — **ровно тот читатель, ради которого
затевалась вся итерация**, — не поставит ни одну из переменных, и каждый запрос
упадёт.

Корень важнее симптома: оверлей (`scripts/sync-example-declarations.ts`) умеет
только **добавлять** переменные через `features.ts` и не умеет **ужесточать**
переменную, которую шаблон объявил необязательной. Поэтому настоящее требование
примера живёт в `place.ts`, а не в схеме. Это единственное место, где
центральное утверждение S7 — «`env.required` выводится из схемы, поэтому
декларация не может отстать» — **фактически неверно**: декларация выведена и всё
равно неправа.

- [x] Дать оверлею способ ужесточать, а не только расширять `applicationVariables`.
- [x] Переменная, которую роль разыменовывает без запасного значения, объявлена
      обязательной: оверлей примера ужесточает её в `features.ts`, и это видно в
      его `project.json`. Отдельного теста нет — свойство держит схема окружения,
      которая упадёт при старте.

### Новое: «второго списка имён» я не убрал

**W-2.** Комментарий в `scripts/dev.ts` и запись S4 утверждают, что второго
списка имён переменных больше нет. Проверено — есть: `developmentEnvironment()`
это рукописное перечисление шести переменных. Имена портов действительно берутся
из декларации, а **значения** — из этого списка.

Следствие: третья роль с `WORKER_PORT` даст `Number(undefined)` → `NaN` →
`Bun.listen({ port: NaN })` → и диагностика соврёт: «Port NaN (WORKER_PORT) is
already in use by another process». Тот же список в этой итерации молча потерял
`INTERNAL_API_URL` и никогда не получал `PUBLIC_API_ORIGIN`, который нужен
dev-запуску примера. Работает это только потому, что `dotenv` в
`config/src/server` наполняет `process.env`, а `inheritToolingEnvironment` его
расплёскивает.

- [x] Удалить перечисление, выводя имена из `env.required` декларации.

### Новое: три пина без зубов

**W-3.** `supervision-signal.test.ts::a role started through a workspace filter
never receives it` **не может упасть по правильной причине**. `stderr: 'ignore'`
на обоих спавнах, и ничто не проверяет, что роль вообще стартовала: если

**W-4.** `project-declaration.test.ts::migrations are declared as bytes, not as a

**X-8. Переименование процессов PM2 без инструкции оператору.** `startOrReload`
поднимет новые имена и **оставит старые работать**; оба комплекта берут те же
порты из того же `.env`, и новые уйдут в crash-loop на `EADDRINUSE` под
`autorestart`. Команды `pm2 delete` нет ни в changelog, ни в README, ни в
`release.ts`.

**X-9. У скаффолдера нет канала миграции вообще.** `assertMigrationSection`
core-only, а стартер выпускает семь breaking-изменений с переименованными
переменными и процессами — без гида и без гейта.

**X-10. Мелкое, подтверждено:** два раздела `### Fixed` в одном `[Unreleased]`;
переименования переменных лежат в `Fixed`, а не в breaking; `README` шаблона всё
ещё велит звать `db:deploy` руками, хотя `pm2:prod` делает это сам; остатки
`app.config.json` в `CONTRIBUTING.md`, в комментарии `local-env.ts` (уезжает в
каждый созданный проект) и в ADR 0070, который до сих пор `Accepted` без пометки
о перекрытии.

**Версии:** ядро 0.59.4 → **0.60.0**, стартер 0.3.3 → **0.4.0**. Порядок релизов
и `catalog.stitchkit: ^0.59.0` в порядке.

## Что сделано

### Блокеры

- [x] **1. Схема строгая.** Все объекты декларации `.strict()`. Неизвестный ключ
      верхнего уровня, опечатка в необязательном поле роли и лишний ключ внутри
      `identity` отвергаются. Мутация: снятие `.strict()` валит тест.
- [x] **2 + расширение валидатора. Граница держится формой по-настоящему.**
      Вместо одной проверки на `://` в одном поле из четырёх — предикат
      `namesAMachine` (схема, protocol-relative host, `~`, буква диска,
      backslash, IPv4, `host:port`), применённый ко **всем** свободным строкам:
      команды, `build.command`, `migrations.engine`, `readinessPath`, пути.
      Мутация: нейтрализация предиката валит 10 тестов.
- [x] **3. Команды стали argv.** `ProjectCommandSchema` = `executable` + `args`.
      Разбиения по пробелу больше нет, генерация идёт через `JSON.stringify`.
      Части команды дополнительно отвергают абсолютный путь, присваивание
      `NAME=value` и голое число (порт).
- [x] **4. Бюджет остановки замкнут.** `assertSupervisionAllowsShutdown` считает
      слив + форс + уборку; локальная политика поднята с 20 000 до 30 000.
      Тест ловит и «таймаут равен полу», и «на миллисекунду меньше бюджета».
- [x] **5. Forwarded origin получил границу доверия.** Хост принимается только
      из `PUBLIC_WEB_ORIGIN` или `PUBLIC_WEB_HOSTS`, протокол сужен до
      `http`/`https`. Smoke переносимости переписан: он доказывает и то, что
      один артефакт обслуживает несколько адресов **в рамках политики**, и то,
      что незаявленный хост отвергается.
- [x] **W-1 (блокер валидатора). Декларация примера больше не лжёт.**
      `applicationVariables` собирается слиянием, поэтому оверлей умеет
      **ужесточать**, а не только добавлять. Пример объявил `INTERNAL_API_URL`,
      `PUBLIC_API_ORIGIN` и `CORS_ORIGIN` обязательными — проверено:
      `required: true` в его `project.json`. Ручная проверка в `place.ts` убрана
      как ставшая лишней.

- [x] **Supervised-полоса в CI.** Да: класс проверок, который нашёлся только
