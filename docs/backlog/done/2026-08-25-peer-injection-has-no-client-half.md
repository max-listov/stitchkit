# Внедрение peers есть у сервера и отсутствует у клиента

## Зачем

0.60.0 добавил `createSocketIOServer({ peers })` с аргументацией, которую стоит
процитировать целиком, потому что она полностью применима ко второй половине:

> Пути назад не было: потребитель, который использует этот адаптер и раздаёт один
> самодостаточный файл на машину без `node_modules`, получал
> `needs the optional peer "socket.io"` при СТАРТЕ, и единственным обходным путём
> было патчить собранный `dist` стичкита — что ломалось всякий раз, когда двигалась
> его внутренняя раскладка.

Ровно то же верно для клиента, и решения нет. В опубликованном 0.60.1:

- `SocketIOPeerLoaders` объявлен только в `dist/server/socket-io-config.d.ts`,
  поле `peers?: SocketIOPeerLoaders` есть только у серверного конфига;
- у `SocketIOClientConfig` (`dist/browser/socket-io.d.ts`) полей `peers` или
  loader нет вообще;
- `dist/index.js` резолвит клиента так:

```js
var SOCKET_IO_CLIENT = "socket.io-client";
var ioLoader = null;
function loadIo() {
  if (!ioLoader) {
    ioLoader = import(SOCKET_IO_CLIENT).then(...)
  }
  return ioLoader;
}
```

Спецификатор — переменная, поэтому бандлер за ней не идёт **по построению**, и
подставить литерал снаружи нечем. Это та же непроходимая ссылка, ради которой
серверная ручка и появилась.

## Кого это задевает

Любой потребитель, который раздаёт самодостаточный CLI или демон, **звонящий** в
сокет, а не принимающий соединения: агент, воркер, синхронизатор, десктопный
клиент. Для него артефакт — один файл, копируемый на машину без `node_modules`,
часто без сети. Сегодня у такого потребителя два выхода, и оба плохие: возить
рядом `node_modules` или переписывать собранный `dist` стичкита при сборке —
второе именно то, что 0.60.0 объявил тупиком.

## Как воспроизвести

1. Проект, который вызывает `createRealtimeClient` (или `createSocketIOClient`)
   и собирается в один файл (`bun build --compile` либо любой бандлер).
2. Запустить артефакт в каталоге без `node_modules`, под Bun с выключенным
   авто-install (`bun --no-install`) или под Node.
3. При первом подключении:
   `stitchkit: createSocketIOClient needs the "socket.io-client" peer`.

Обратить внимание: выключенный авто-install обязателен, иначе Bun вытянет
недостающий peer из кеша машины разработчика и проба будет ложно зелёной.

## Результат

- У клиентского конфига появляется симметричная ручка — например
  `peers: { client: () => import('socket.io-client') }` — так что литерал живёт
  в исходнике потребителя, где его видит его собственный бандлер.
- Пропуск поля не меняет ничего: ленивый резолв остаётся дефолтом, и проект,
  который никогда не открывает сокет, по-прежнему не обязан ставить peer.
- Симметрия названа в документации: у обеих половин адаптера одна и та же ручка
  и одна и та же причина.

## Как проверить

Тем же способом, каким проверена серверная половина: парой в consumer-lane —
артефакт с внедрёнными loader'ами стартует и **подключается** в каталоге без
`node_modules` под Node и под Bun с выключенным авто-install, а та же программа
без loader'ов там же обязана упасть.

## Почему это стоит того

Аргумент здесь не новый — он уже принят для сервера. Отсутствие второй половины
означает, что потребитель, у которого и брокер, и клиент едут одним артефактом,
всё равно вынужден держать патч собранного `dist` — то есть ровно тот обход,
который релиз 0.60.0 закрывал.

## Что сделано

### Core
- [x] `SocketIOClientPeerLoaders` + `SocketIOClientConfig.peers` в
      `packages/core/src/browser/socket-io.ts`; проходит и через
      `createRealtimeClient`. Пропуск поля не меняет ничего — ленивый резолв
      остаётся дефолтом.
- [x] Loader объявлен `() => Promise<unknown>` и проверяется на границе, ровно
      как `SocketIOPeerLoaders.bunEngine`: корневой entrypoint браузеро-безопасен,
      и его декларации не должны называть `socket.io-client` — иначе потребитель,
      который никогда не открывает сокет, обязан ставить пакет только чтобы
      **тайпчекнуться**. Это поймал бюджет пиров consumer-lane.
- [x] Внедрённый loader мемоизируется **на клиента**, а не в модульный кеш: два
      клиента в одном процессе могут быть собраны разными бандлами.
- [x] Loader, вернувший не тот модуль, отвергается по имени, а не падает позже
      как `io is not a function`.
- [x] `isModuleNotFound` вынесен в `packages/core/src/internal/optional-peer.ts`
      и используется обеими половинами: ошибка loader'а по своим причинам
      проходит наружу нетронутой и не выдаётся за проблему упаковки.

### Fixed по ходу
- [x] Неудачный резолв пира больше не роняет процесс. Раньше это была
      необработанная rejection: отсутствующий `socket.io-client` убивал процесс
      на первом `connect()`, печатая `Cannot find package` — не тот текст,
      который для этого написан. Теперь идёт в `onConnectError` с
      `terminal: true`, а `desiredConnected` сбрасывается, чтобы поздний
      `connect()` мог начать заново. Без хука по-прежнему пробрасывается — тихо
      не становится.

### Tests

      peer injection», 5 тестов: внедрённый loader реально подключается и делает
      round-trip; отсутствующий пакет доходит до `onConnectError` с правильным
      советом; не тот модуль отвергается по имени; чужая ошибка проходит

- [x] `packages/core/scripts/consumer-lane/self-contained-socket-client.mjs` —

      Node и под Bun с `--no-install`; тот же артефакт без loader'а там же
      обязан упасть с именем пира. Фальсифицировано: реализация, игнорирующая
      внедрённый loader, роняет положительную половину.
