# Обычный bun update растворяет catalog, и узнаёшь об этом сильно позже

## Зачем

Единственное место, где записан диапазон Stitchkit для шаблона, — блок
`catalog` в корневом манифесте; все манифесты ссылаются на него через
`"stitchkit": "catalog:"`. Это и есть инвариант, ради которого существует
`assertCatalogIsTheOnlyStitchkitRange`.

`bun update` его ломает. Дважды за один день:

- `bun update --latest` растворил `catalog:` в литеральные диапазоны **во всех
  шести манифестах** сразу;
- `bun update stitchkit` — в одном.

Гейт оба раза сработал, то есть система здорова. Больно другое: между поломкой
и сигналом лежит полный прогон полос, а починка — ручной откат манифеста,
который надо ещё догадаться сделать, а не просто перезапустить команду.

Отдельная деталь того же захода: `bun update stitchkit` вернул 0.60.0, хотя
реестр уже отдавал 0.60.1 — то есть у обновления есть ещё и своя несвежесть,
и на неё легко списать симптом, приняв растворённый catalog за норму.

## Результат

- Обновление зависимостей шаблона выполняется одной командой проекта, а не
  сырым `bun update`.
- Она обновляет то, что просили, и возвращает `catalog:` на место, а не
  оставляет это человеку.
- Инвариант проверяется **сразу после** обновления, а не через полосы: сигнал
  приходит там же, где сделано действие.
