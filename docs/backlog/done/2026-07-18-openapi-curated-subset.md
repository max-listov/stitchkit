# `generateOpenApiDocument` — курируемое подмножество методов

## 1. Запрос (generic)

`generateOpenApiDocument` сейчас берёт **все** HTTP-exposed методы скормленных
сервисов — фильтра нет (`server/openapi.ts:132`: пропускается только не-HTTP
`expose`). Нужна возможность отдать **курированное подмножество**: публичный
`/openapi.json`, показывающий ровно разрешённые методы и **не раскрывающий
существование остальных** (внутренние `auth` / `users` / `payments` / …).

Кейс, на котором всплыло: внешним клиентам выдаётся API-ключ с доступом к
нескольким методам (`scope: 'account'`); публичная спека должна показывать
ровно их, а не весь surface. Сейчас спека — «всё или ничего».

Требование: генерённая спека должна быть **фильтруемой по явной пометке**, а не
полной проекцией всех HTTP-методов.

## 2. Пути решения

### Вариант 1 — first-class поле `public?: boolean` на методе + опция `onlyPublic`

`generateOpenApiDocument({ services, onlyPublic: true })` включает только методы
с `public: true`.

- ✅ Декларативно, эргономично для частого кейса.
- ❌ **Вшивает доменное понятие видимости в generic-ядро** — противоречит
  ADR 0002 (no domain model) и `coding-standards §31` (не выдумывать
  классификации, которых не просили; фреймворк уже обжигался на ролях
  `prod|dev`). Почему `public`, а не `visibility: public|partner|internal`? Один
  булев флаг открывает scope creep, который ядро не должно на себя брать.
- ❌ Дублирует существующие оси `expose` (транспорт) и `scope` (auth) третьей
  осью, которая по сути — **политика консьюмера**, а не свойство контракта.

### Вариант 2 — предикат `includeMethod: (method: MethodDef) => boolean` (РЕКОМЕНДУЮ)

`generateOpenApiDocument({ services, includeMethod: (m) => m.meta?.public === true })`.

- ✅ **Ноль новых семантик в ядре** — политику решает приложение, ядро остаётся
  generic (дух ADR 0002).
- ✅ Предикат получает `MethodDef`, где уже есть **всё** для любой политики:
  `scope`, `meta`, `annotations`, `key`, `serviceName`, `path`. Один примитив
  покрывает и этот кейс, и будущие оси (partner-tier, deprecated-hidden, …) без
  изменений ядра.
- ✅ **Декларативность на контракте — через уже существующий `meta`** (ADR 0021,
  opaque app-метаданные): `meta: { public: true }` на эндпоинте → один источник,
  ноль дрейфа. Это эргономика Варианта 1, полученная через примитив Варианта 2 +
  существующий механизм, без нового поля ядра.

## Лучший вариант и почему

**Вариант 2 (предикат) как основной примитив + декларативность через `meta`.**
Он покрывает кейс 1-в-1, остаётся generic (ADR 0002), не вводит доменную
классификацию (§31) и не открывает дверь scope creep. `public`-поле не нужно —
его роль играет `meta.public`. Вариант 1 отвергнут как нарушающий generic-ядро.

### ⚠️ Обязательная оговорка — это НЕ контроль доступа

Фильтр управляет только тем, что **рекламируется** в `/openapi.json`. Реальный
гейт остаётся на auth-хуке (`scope`). Спрятать эндпоинт из спеки ≠ защитить его:
без scope-гейта он всё ещё вызываем. Две независимые вещи, обе обязательны:
дока-фильтр = «не палим существование», auth-scope = «не пускаем». Это должно
быть явно в доке фичи, чтобы никто не принял фильтр за защиту.

## 3. Пошаговый план реализации

1. **Ядро** — `OpenApiConfig.includeMethod?: (method: Readonly<MethodDef>) => boolean`
   в `server/openapi.ts`. В цикле обхода методов (`openapi.ts:131`), сразу после
   HTTP-фильтра (строка 132): `if (config.includeMethod && !config.includeMethod(method)) continue;`.
   **Guard-коммент у хука:** «любой будущий `$ref`-дедуп схем (ADR 0018) обязан
   идти ПОСЛЕ этого фильтра, иначе схемы исключённых методов утекут». Дефолт без
   опции = текущее поведение → аддитивно, ноль breaking.
2. **Экспорт типов** — `includeMethod` в публичном `OpenApiConfig` (уже
   экспортируется из `/server`, `index.ts:70`); reference-гард потребует строки в
   `reference.md:243`.
3. **Доки** — раздел «Curating the spec» (где живёт OpenAPI): (а) рекомендованный
   паттерн `meta: { public: true }` + `includeMethod`; (б) **паттерн двух
   документов** — внутренний полный + публичный фильтрованный, две раздельные
   route (иначе не-фильтрованный `openApiRoute` палит всё); (в) **явное
   предупреждение фильтр-≠-auth** (прячет из спеки, НЕ защищает — гейт на
   `scope`). Обновить reference.md (`OpenApiConfig`).
4. **Тест** — `openapi.test.ts`: (а) спека с `includeMethod` содержит ровно
   помеченные `paths`, непомеченные `paths` **отсутствуют**; (б) инлайн-схема
   исключённой операции **не появляется нигде** в JSON (не «components» — их
   нет — а именно форма данных скрытого метода); (в) дефолт без предиката не
   изменился (byte-identical).
5. **CHANGELOG** — `### Added` (аддитивно, minor bump, без `⚠️ Breaking`).
6. **`onlyPublic` / `public`-поле — НЕ добавлять сейчас.** §31: сахар потом
   дёшев, выпил из всех слоёв — дорог. Если `meta.public` станет повсеместным по
   флоту (3+ потребителя) — тогда тонкий `onlyPublic: true` поверх предиката.

## Провалидировано (адверсариальный сабагент, 2026-07-18) — вердикт AGREE-WITH-CHANGES

Все load-bearing claims подтверждены по исходнику:
- **`meta` доходит до `MethodDef`** — `EndpointDefBase.meta` (`define.ts:66`) →
  `implement`: `meta: endpoint.meta` (`implement.ts:49`) → `MethodDef.meta`
  (`types.ts:71`); генератор итерирует ровно этот `method` (`openapi.ts:131`).
  Паттерн `meta.public` держится.
- **Точка хука верна** (`openapi.ts:132`, рядом с HTTP-фильтром), `method` в
  скоупе, дефолт без опции байт-в-байт идентичен.
- **Отклонение Варианта 1 корректно.** `expose` — это выбор среди **транспортов
  фреймворка** (ядро обязано их моделировать для роутинга), а `public` —
  **аудитория консьюмера** (ядро не имеет на неё ни транспорта, ни dispatch).
  Не прецедент. `meta.public` = textbook-использование ADR 0021.
- **Security-фрейминг точен**, naming `includeMethod` лучше `filter` (полярность
  явная).

### Правки в план (обязательны до реализации)

**A. Утечки схем НЕТ — by construction (не «открытый вопрос», а решённый факт).**
Схемы **инлайнятся** в каждую операцию (`openapi.ts:173,215`; ADR 0018 §45-46
«Schemas are inlined, not de-duplicated into `components/$ref`»); общего раздела
`components/schemas` в генераторе нет вообще (ноль вхождений `components`).
`continue` выкидывает весь `paths[fullPath]` вместе с инлайн-схемами → ничего не
остаётся. ⚠️ **Регресс-tripwire:** если когда-нибудь добавят `$ref`-дедуп
(ADR 0018 его отложил), он ОБЯЗАН идти **после** `includeMethod`, иначе утечка
станет реальной — поставить коммент у точки хука.

**B. `openApiRoute` — не no-op, а footgun.** `openApiRoute` (`openapi.ts:238-244`)
замыкает **статический** `document`, захваченный при монтировании. Значит фильтр
работает только если скормить **отфильтрованный** документ. Реальный риск: один
смонтированный `openApiRoute` от **не**фильтрованного `generateOpenApiDocument`
палит всё, сколько бы `includeMethod` ни существовал. Доки ОБЯЗАНЫ показать
**паттерн двух документов**: внутренний (полный) + публичный (фильтрованный), две
раздельные route. Иначе фича — заряженное ружьё.

### Мелочи (учесть)

- Тип: `includeMethod?: (method: Readonly<MethodDef>) => boolean` — bare
  `MethodDef` (= `MethodDef<unknown,unknown,unknown>`, как `ServiceDef.methods`),
  `Readonly` сигналит «предикат не мутирует».
- Второй аргумент с `pathPrefix` — НЕ нужен пока; `method.path`+`serviceName`
  покрывают. Не усложнять.
- Аддитивно → `### Added` + minor bump, без `⚠️ Breaking` (подтверждено).
