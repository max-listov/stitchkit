# Потребитель может вшить Socket.IO peers в самодостаточный артефакт

## Зачем

`packages/core/src/server/socket-io.ts` держит peers в переменных сознательно, и обе причины верны:

- потребитель, бандлящий не связанный с сокетами экспорт `stitchkit/server`, не должен резолвить
  необязательные peers;
- `@socket.io/bun-engine` — Bun-only, и top-level value-import уронил бы весь barrel на Node ещё до
  того, как дело дойдёт до сокетов.

Чего нет — обратного пути. Потребитель, который **именно этот адаптер и использует**, а поставляется
одним самодостаточным файлом на машину без `node_modules` и часто без сети, не может сказать об этом
фреймворку. `import(SOCKET_IO_SERVER)` бандлер статически не проследит, поэтому пакет в артефакт не
попадает, и отказ приходит не при сборке, а при старте:

```
error: [stitchkit] createSocketIOServer needs the optional peer "socket.io"
```

Единственный доступный сегодня обход — патчить **собранный dist stitchkit** на этапе сборки,
подменяя `import(КОНСТАНТА)` на литерал. Это работает и ломается при каждом внутреннем изменении
раскладки: у одного из потребителей серверная пара переехала в другой бандл, патч перестал её
покрывать, артефакт собрался, агент работал, брокер не стартовал вовсе.

Ошибка вдобавок трудно ловится на машине разработчика: Bun резолвит недостающий peer из install-кеша,
поэтому и сборка, и локальный запуск, и даже интеграционный харнесс остаются зелёными — падает
только нода, у которой такого кеша нет.

## Результат

- `createSocketIOServer` принимает необязательные загрузчики peers:

  ```ts
  createSocketIOServer({ ...config, loadServer: () => import("socket.io") })
  ```

  Литерал написан у потребителя, поэтому его бандлер видит импорт статически и вшивает пакет.
  Дефолт остаётся ленивым: для всех, кто сокеты не использует, не меняется ничего.
- Опционально поверх — экспорт со статическими импортами (например `stitchkit/server/socket-io`) для
  типового случая. Node-безопасность сохраняется: Bun-only код живёт за отдельным путём, а barrel
  `stitchkit/server` не трогается.
- В optional-peer матрице (`docs/guide/testing-and-deployment.md`) появляется строка про
  самодостаточный артефакт, а к негативному missing-peer доказательству добавляется положительное:
  артефакт, собранный с инъекцией загрузчиков, **стартует с отключённым auto-install**. Без этого
  условия проверка доказывает свойство машины, а не артефакта.

## Открытые развилки

- **Инъекция, отдельный экспорт или оба.** Инъекция — минимальное изменение API и работает с любым
  бандлером; экспорт удобнее в типовом случае, но плодит поверхность.
- **Форма загрузчика.** Функция, возвращающая модуль, либо уже разрешённый модуль. Первое сохраняет
  ленивость и порядок инициализации, второе проще типизировать.
- **Проверка в CI.** Отдельный smoke, собирающий крошечный артефакт и запускающий его под
  `--no-install`, либо расширение существующей матрицы.

## Что сделано

### Решения по трём развилкам

- [x] **Инъекция, а не отдельный экспорт.** Минимальное изменение поверхности,
      работает с любым бандлером, и не заводит второй способ делать то же самое.
      `stitchkit/server/socket-io` со статическими импортами не завёл: он был бы
      удобнее ровно в одном типовом случае и стоил бы постоянной второй точки
      входа, которую пришлось бы держать согласованной. Вернуться можно, если
      типовой случай окажется частым.
- [x] **Функция, возвращающая модуль.** Уже разрешённый модуль сломал бы обе
      вещи, ради которых peers ленивые: ничего не грузится, пока адаптер не
      попросит, и на Node bun-engine не запрашивается вовсе.
- [x] **Отдельный smoke, а не строка матрицы.** Матрица классифицирует бюджеты
      точек входа; это свойство **артефакта**, другой предмет. И собственный
      проект вместо чужой фикстуры: одна из них специально запрещает
      `@socket.io/bun-engine`, и занять её ради сборки этого пакета значило бы
      сломать проверку, ради которой она существует.

### Ядро

- [x] `SocketIOPeerLoaders` в `packages/core/src/server/socket-io-config.ts`:
      `peers.server` и `peers.bunEngine`, обе опциональны, дефолт не меняется.
- [x] `bunEngine` типизирован как `() => Promise<unknown>` и проверяется по форме
      на границе в `socket-io.ts` — **не** для красоты: тип из Bun-only пакета в
      runtime-нейтральном модуле попадает в декларации `stitchkit/node`, и
      бюджет peer-матрицы это поймал на первом же прогоне. Границу держит
      `isBunEngineModule`, а не каст.
- [x] Диагностика различает два случая, потому что у них разные исправления:
      дефолтная загрузка не нашла пакет — ставь его на машину; **инъецированный**
      загрузчик не нашёл — артефакт его не содержит, и совет «поставь пакет»
      отправил бы читателя не туда. У дефолтного сообщения теперь есть вторая
      фраза про `peers` — оператор, который упёрся в это на машине без
      `node_modules`, как раз и есть тот, кому она нужна.
- [x] Тип экспортирован из `stitchkit/server` и `stitchkit/node`, задокументирован
      в `docs/api/reference.md`, снимок публичной поверхности обновлён.

### Доказательство

- [x] `packages/core/scripts/consumer-lane/self-contained-socket.mjs` — шаг
      consumer-полосы. Собирает программу с инъекцией, кладёт **один файл** в
      каталог, у которого ни на одном уровне выше нет `node_modules` (проверяется
      явно — первая версия проверки прошла бы против пустого бандла, потому что
      `node_modules` фикстуры лежал тремя уровнями выше), и запускает под Node и
      под Bun с `--no-install`.
- [x] Проверяется **парой**: та же программа без инъекции обязана там упасть.
      Без отрицательной половины положительная доказывала бы свойство машины —
      ровно то, из-за чего дефект и не виден в разработке, где Bun добирает
      недостающий peer из install-кеша.
- [x] Артефакт собирается **под каждый рантайм отдельно**: bun-таргетный бандл
      на Node не запускается (`__require is not a function`) — это выяснилось
      исполнением, а не рассуждением. И на Node bun-engine не инъецируется: его
      там никто не спрашивает, а бандлить Bun-only пакет под Node значит просить
      бандлер тащить `bun:`-импорты.
- [x] Диапазоны версий берутся из `peerDependencies` самого пакета, поэтому
      проверка не может разойтись с тем, что сказано потребителю.
- [x] Проверено мутацией: со снятым `config.peers?.server` полоса краснеет.

### Найдено попутно

- [x] Сканер деклараций в peer-матрице искал импорты регуляркой по сырому тексту
      `.d.ts` и считал зависимостью пример `import('@socket.io/bun-engine')`
      **внутри JSDoc**. Ложное срабатывание, которое давит на автора писать
      документацию хуже. Теперь перед поиском снимаются блочные комментарии и
      строчные, начинающие строку, — обе формы однозначны и не могут проглотить
      импорт.

### Тесты
