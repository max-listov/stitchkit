# runtime:smoke проходит по пути README, а не только в полосе

## Зачем

Воспроизведено на потребителе стартера 0.4.0, свежая интеграция (2026-08-25). README раздела
«Gates» перечисляет пять команд подряд, включая `bun run runtime:smoke`, — как будто их можно
выполнить сверху вниз. По факту smoke из коробки падает дважды:

1. **Роли не подняты.** `runtime:smoke` стучится в `SMOKE_API_ORIGIN` и получает `ECONNRESET`:
   он проверяет ЖИВОЙ deployment, но README не говорит ни что роли надо поднять, ни какой
   командой. В CI это делает полоса — у пользователя полосы нет.
2. **Дефолтный allowlist не пускает placement-смок.** `.env.example` даёт
   `PUBLIC_WEB_HOSTS=127.0.0.1:3210`, а `assertArtifactIsPlacementFree` шлёт
   `x-forwarded-host: alpha.example` и `beta.example:8443` — веб-роль честно отказывает
   («Refusing to answer for host…»), смок падает на 500. Механика верная, но пользователь
   README-пути видит красный гейт на нетронутом скаффолде и не знает, что это про его env.

Мелочь рядом: зелёный прогон печатает
`Client.listTools() called but server does not advertise tools capability - returning empty list` —
предупреждение вендорного клиента на пустом шаблоне без tools. Непонятно, норма это или дефект;
шум в единственной строке успеха гейта.

## Результат

- Путь README выполняется сверху вниз на свежем скаффолде: либо smoke сам поднимает роли на
  эфемерных портах и сам подставляет нужный allowlist (предпочтительно — и стыкуется с
  «полоса убирает всё, что подняла»), либо README честно описывает предусловия командой.
- Несовпадение allowlist'а диагностируется у смока: вместо голого 500 — «поднимите роль с
  PUBLIC_WEB_HOSTS=…», с точным списком.
- Warning про listTools либо снят (blank-шаблон не зовёт listTools без tools), либо назван в
  выводе ожидаемым.

## Что сделано

Оба симптома подтвердились, и под вторым нашлась третья причина, которой в
отчёте не было. Проверялось не рассуждением, а прогоном: свежий скаффолд,
одноразовая база, изолированный `PM2_HOME`, и весь блок Gates подряд, как его
читает человек.

### 1. Список Gates был невыполним, и не только из-за отсутствующей команды

`runtime:smoke` и `e2e` проверяют **живой** deployment, а в списке не было
ничего, что его поднимает. Но когда я дописал в список `bun run dev`, прогон
всё равно упал тем же `ECONNRESET`: **`bun run dev` печатал «development
processes are running» в момент spawn'а.** PM2 возвращает управление сразу,
роли начинают слушать секундами позже, — то есть скрипт утверждал то, чего не
проверял, а следующая команда списка попадала в закрытый порт. `bun run
pm2:prod` вёл себя так же.

- [x] `scripts/readiness.ts` (новый) — `declaredRoleReadiness()` берёт адрес
      готовности каждой роли из декларации (`portVariable`, `bindVariable`,
      `readinessPath`), `awaitRolesAnswering()` ждёт ответа. `0.0.0.0` — это то,
      что роль **биндит**, дозваниваться туда нельзя, поэтому дозвон идёт на
      loopback. Роль с listener'ом и без порта — ошибка, а не тихий пропуск.
- [x] `scripts/dev.ts` и `scripts/release.ts` печатают «running» / адреса
      только после того, как роли ответили.
- [x] `README.md` и `AGENTS.md`: список Gates теперь выполняется сверху вниз и
      содержит `bun run pm2:prod` между `build` и двумя runtime-гейтами —
      потому что deployment, о котором эти гейты, это только что собранный
      артефакт. `bun run dev` в этой роли отдельно назван как то, что скармливает
      Playwright dev-сборку: 4 из 33 e2e падали на компиляции маршрута по
      первому запросу, то есть измеряли тайминг, а не поведение.

### 2. Смок требовал, чтобы deployment заранее доверял его выдуманным хостам

`assertArtifactIsPlacementFree` слал `x-forwarded-host: alpha.example` и
`beta.example:8443` — два фикстурных имени, зашитых в чек. Дозвониться по
адресу, которого нет в `PUBLIC_WEB_HOSTS`, нельзя: политика отказывает, и
правильно делает. Значит чек проходил только там, где кто-то отдельно вписал в
allowlist эти же два имени — а это была **только упакованная полоса**. Два
экземпляра одной фикстуры, обязанные совпадать через два репозитория.

- [x] `scripts/web-surface-smoke.ts`: `planPortabilityCheck()` читает
      `PUBLIC_WEB_HOSTS` и берёт адреса, которые deployment **сам** заявил.
      Направление связи перевернулось: deployment объявляет, чек читает.
- [x] Адресов меньше двух — это `refuse` с точной строкой:
      `PUBLIC_WEB_HOSTS=<текущий>,alpha.example,beta.example:8443` и командой
      перезапуска. Отказ происходит **до** первого запроса, поэтому 500 в этом
      сценарии больше невозможен по построению, а не по удаче.
- [x] `PUBLIC_WEB_ORIGIN` закрепляет один origin, и тогда переносимость по
      запросу ненаблюдаема. Это законная конфигурация: `skip` с названной
      причиной, а не ложный диагноз.
- [x] Подделанный хост выбирается так, чтобы его гарантированно не было в
      allowlist: иначе отказ, ради которого чек существует, не наступает, и
      утверждение становится невыполнимым.
- [x] `_env.example` заявляет два примерных хоста с объяснением, зачем они и
      что в production их место занимают настоящие имена, — чтобы гейт
      сгенерированного проекта был взведён из коробки, а не молча пропускал
      главную проверку.
- [x] `scripts/deployment-preflight.ts` (новый): до первого чека сказано, что
      именно не слушает и какой командой это поднять.

### 3. Warning про listTools

- [x] `scripts/surface-conformance.ts` спрашивает `getServerCapabilities()`
      прежде чем звать `listTools()`. Сервер без MCP-инструментов не
      анонсирует capability `tools` — это его собственное утверждение, оно
      наблюдается вместо вендорной debug-строки и даёт тот же ответ. Манифест,
      заявляющий MCP-инструмент, по-прежнему падает против него.
