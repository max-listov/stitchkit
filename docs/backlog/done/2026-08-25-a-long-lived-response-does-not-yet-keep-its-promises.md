# Долгоживущий маршрут не держит трёх обещаний, которые сам даёт

## Зачем

Примитив `streamingRoute` / `ndjsonRoute` / `sseRoute` документирует четыре
вещи, которые берёт на себя. Ревью показало, что три из них он не выполняет —
и каждый случай подтверждён пробником, а не рассуждением.

**1. Заголовки склеиваются, а не заменяются.** JSDoc на `StreamingRouteOptions.headers`
говорит «the framing headers below cannot be overridden». Это неправда:
ключи в spread чувствительны к регистру, а `Headers`, собранные из записи,
**дописывают**, а не перезаписывают.

```
{ ...{'content-type':'text/plain; charset=utf-8'}, 'Content-Type':'application/x-ndjson' }
→ content-type: "text/plain; charset=utf-8, application/x-ndjson"
```

Потребитель, написавший `headers: { 'content-type': 'application/x-ndjson; charset=utf-8' }`
— строчное написание самое обычное — отдаёт наружу битый тип. То же с
`cache-control: max-age=99, no-cache`, что для промежуточного узла просто
противоречие. Ни один тест этого не ловит: они проверяют `content-type` только
когда `headers` не передан, а fixture consumer-lane намеренно берёт
неконфликтующий `x-consumer`.

**2. Нет backpressure.** Насос — отсоединённая петля по `iterator.next()` с
безусловным `controller.enqueue`; `pull` не реализован, `desiredSize` не
читается. Пробник: источник на 200 000 кадров по ~200 байт против клиента,
который открыл ответ и не прочитал ни байта, отработал до конца за 3 с, RSS
251 МБ. Ничто не притормозило. Любой источник быстрее сети — хвост лога,
реплей при подписке, всплеск на нагруженном топике — плюс один медленный
потребитель = весь всплеск в памяти сервера на каждое соединение. В файле
подробно расписаны четыре других опасности; про эту не сказано нигде.

**3. Отмена не доходит до сервера при чтении так, как учит гайд.** `parseNDJSON`
в `finally` освобождает lock, но не отменяет тело. Соединение остаётся
открытым, `request.signal` на сервере не абортится, `release()` не
выполняется. Пробник: клиент делает `break` после двух кадров — через две
секунды `finally` серверного генератора **не отработал**. Задокументированная
идиома в `docs/guide/client.md` — голый `fetch` + `for await`, без
`AbortController` — то есть потребитель, следующий гайду буквально, отписаться
не может вообще. А весь смысл примитива записан в его же шапке: «ушедший
подписчик не оставляет живой работы на сервере».

## Результат

- Заголовки обрамления действительно нельзя переопределить — либо они
  выигрывают без учёта регистра, либо конфликт отвергается явно, но склейки
  не остаётся.
- Поток ограничен: медленный или замерший потребитель не может заставить сервер
  буферизовать неограниченно.
- Отмена доходит до источника при **любом** нормальном способе прекратить
  чтение, включая тот, что показан в гайде; если какой-то способ этого не даёт,
  гайд показывает тот, который даёт.
- Всё, что примитив на себя не берёт, названо в исходнике и в гайде.

## План

- [x] Заголовки: собирать `Headers` и `set()` обрамляющие поверх пользовательских,
      либо отфильтровывать конфликтующие ключи без учёта регистра.
- [x] Backpressure: перевести выдачу кадров на `pull`, чтобы очередь была
      ограничена; пульс при заполненной очереди пропускать — он нужен простою,
      а не замершему потребителю. Проверено пробником: `cancel()` доставляется
      и при подвешенном `pull`.
- [x] `parseNDJSON`: отменять тело при выходе из цикла, а не только отпускать
      lock; согласовать с гайдом.
- [x] Мелочи того же класса: `release()` завернуть в try/catch (рукописный
      `AsyncIterable` с синхронным или бросающим `return()` роняет
      необработанную rejection из отсоединённой петли); проверять
      `request.signal.aborted` до подписки на `abort` — на уже прерванном
      сигнале слушатель не сработает никогда.

## Acceptance

- [x] Тест: пользовательский `content-type` в нижнем регистре не порождает
      склеенное значение.
- [x] Тест: быстрый источник против нечитающего потребителя не растёт
      неограниченно.
- [x] Тест: `break` из `for await (… parseNDJSON …)` закрывает источник на
      сервере.
- [x] `bun run verify` зелёный.

## Что сделано

### Core
- [x] Заголовки собираются через `Headers` и обрамляющие ставятся `set()` —
      замена без учёта регистра вместо склейки.
- [x] Backpressure: насос ждёт спроса (`pull` будит), очередь ограничена
      `MAX_BUFFERED_FRAMES = 16`, пульс пропускается при заполненной очереди.
- [x] `parseNDJSON` отменяет тело, а не только отпускает lock.
- [x] `release()` завёрнут в try/catch и терпит рукописный `AsyncIterable`;
      добавлена проверка `request.signal.aborted` до подписки.

### Найдено собственным пробником по ходу — и оказалось хуже исходной находки
- [x] **Всегда готовый источник голодал event loop.** `await iterator.next()` у
      генератора, который никогда не ждёт, разрешается микротаском, поэтому цикл
      крутился без единого хода event loop: **19,5 млн кадров и `fetch`, который
      не вернулся вообще**. То есть пункт 3 — «заголовки при открытии» — тихо
      переставал быть правдой ровно для того источника, которому есть что
      сказать. Это было и до правок ревью. Насос отдаёт ход рантайму каждую
      полную очередь.
- [x] Попутно выяснено, что путь через `pull` — учебниковая форма — здесь не
      работает: с всегда готовым источником рантайм не успевает отдать ответ, и
      `fetch` не возвращается. Поэтому насос остался, а backpressure сделана
      явной.

### Приведено к правде, а не замазано
- [x] `break` из цикла отменяет тело, но **до сервера под Bun доходит не сразу**
      — измерено, источник жил секунды. Гайд и JSDoc теперь показывают
      `AbortController` как способ отписаться, а тест утверждает ровно то, что
      читатель может гарантировать: тело отменено.

### Tests
- [x] `streaming-route.test.ts` — 11 тестов. Новые: заголовки любого регистра,
      всегда готовый источник (не голодает и ограничен), отмена тела при `break`,
      нецелый `idleTimeoutSeconds`, и **изолирующий тест на снятие таймаута**
      (пульс заведомо длиннее порога).
