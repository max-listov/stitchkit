# Репозиторий не игнорировал то, что производит его собственный шаблон-workspace

## Зачем

Замечено владельцем: во время прогона в дереве stitchkit на секунды появлялась
куча файлов от Playwright, видимых в git, и потом исчезала.

Причина не в Playwright. `packages/create-stitchkit/template` — не инертные
данные, а рабочий проект: в нём запускаются `bun run build`, `bun run e2e` и
`bun run acceptance:local`, и каждый из них пишет вывод **внутрь дерева
репозитория**. Правила, которые этот вывод прячут, лежат в
`template/_gitignore` — а git здесь такого имени не читает: файл становится
`.gitignore` только после генерации проекта.

Следствия, все три подтверждены:

1. `test-results/` наполнялся артефактами прогона и был виден как untracked
   содержимое репозитория; Playwright чистит директорию в конце — отсюда
   «появились и пропали».
2. `.last-run.json` из этой директории оказался **в индексе** (среда стажирует
   после каждого шага), то есть один шаг отделял артефакт прогона от коммита.
3. `*.log` не был закрыт вообще: в корневом списке стояло `_.log`, что
   совпадает с файлом, буквально названным `_.log`. Рядом тем же способом был
   испорчен `report.[0-9]*.[0-9]*.[0-9]*.[0-9]*.json`.

Это тот же класс, что и уехавший в шаблон `.build-stamp.json`: один список
«что никогда не путешествует» и несколько потребителей, из которых проверялся
не каждый. Здесь третий потребитель — git этого репозитория.

## Результат

- Корневой `.gitignore` закрывает всё, что закрывает `template/_gitignore`.
- Расхождение между этими двумя списками роняет сборку, а не всплывает у
  владельца в `git status`.
- Сломанные шаблонные шаблоны (`_.log`, `report.[0-9]_…`) исправлены.
