## Зачем

Два независимых расхода контекста, наблюдаемые на живых прогонах:

1. Каждый запрос несёт полные JSON-схемы всех смонтированных инструментов — и тех, что нужны
   каждый ход, и тех, что вызываются раз за сессию. Потребитель уже считает их цену
   (`toolSchemaTokens`), но повлиять на неё не может.
2. Модель не знает своего бюджета. В наблюдаемом прогоне модель ушла в обрыв по переполнению,
   не изменив поведения ни на одном ходе до него: ей неоткуда было узнать, что пора сжиматься
   или заканчивать.

## Ресерч 2026-09-01

Половина этой таски уже выпущена, и это меняет её состав.

**Отложенные схемы существуют с 0.69.0**: `createDeferredAgentToolSurface` (ADR 0129, раздел
гайда «Bounded deferred tool catalogs», экспортировано из `stitchkit/agent-runtime`). Первый шаг
несёт только bounded search-tool, alwaysOn-имена и dynamic pins; активация durable (переживает
recovery, выводится из истории); вызов неактивного инструмента уже сегодня РЕМОНТИРУЕТСЯ в
search-вызов с `reason: 'inactive_call'` (`deferred-tools-internal.ts`) — ровно та «подсказка
вместо ошибки», которую просит Результат.

Потребитель на 0.70.5 считал `toolSchemaTokens` и фичу не нашёл. Значит первый пункт таски — не
реализация, а **доставка до потребителя**: убедиться, что через headless-харнес путь проходит
(`tools(runContext)` + `loop.prepareStep` доступны — проверено по `harness-contract.ts:77,91`),
и что рецепт виден там, где смотрит агент потребителя (guide → llms.txt уже генерирует его;
проверить, что раздел находится по словам, которыми ищут: «schema tokens», «deferred», «tool
budget»).

**Второй пункт — настоящий пробел.** Runtime знает бюджет (`contextWindow`, `reservedOutput` —
`prompt.ts:44`, харнес заполняет из дескриптора модели `harness.ts:142`), считает usage с
provenance-словарём, умеет отказывать по переполнению (`AgentContextOverflowError`) — но модели
не сообщает ничего до самого обрыва. Референсный харнес (тот, в котором написан этот план)
решает это пассивной строкой в системном контексте — `<total_tokens>N left</total_tokens>` каждый
ход, без отдельного инструмента; наблюдаемо, что модели на неё реагируют сжатием и завершением.
Пассивная строка дешевле tool-вызова и не требует от модели догадаться спросить.

## Результат

- Существующая deferred-поверхность доказуемо доступна из headless-харнеса и находима: рецепт в
  harness-разделе гайда, acceptance-тест «первый запрос несёт только search + alwaysOn» через
  харнес, а не только через голый runtime.
- Runtime отдаёт `contextUsage { usedTokens: {value?, provenance}, contextWindow,
  reservedOutput }`. **Дроби нет** — деление делает рендер потребителя: дробь, производная от
  estimated-компонента, не может быть голым числом, а отдавать `{value?, provenance}` ради
  деления — лишняя сущность (внесено валидацией: первая редакция несла `fraction` без provenance
  рядом с provenance-полным `usedTokens` — внутреннее противоречие).
- Числитель — `inputTokens` ПОСЛЕДНЕГО `finish-step`, не кумулятивная сумма шагов (гайд сам
  предупреждает об этой подмене); на первом шаге run'а provider-reported нет — `usedTokens`
  честно `unavailable` либо целиком estimate от token-count'ов композиции, с provenance
  `estimated`. Schema-байты инструментов, активированных ЭТИМ шагом deferred-поверхностью,
  отстают на шаг — тест фиксирует это как известное свойство, а не заметает.
- Отрисовка: пассивная строка — ХВОСТОВОЕ размещение (внутри user-контента в конце), не смена
  system: (а) SDK отказывает system-роли внутри messages — на этом уже горели; (б) смена system
  каждый шаг инвалидирует provider prefix cache всего разговора — кратный рост цены длинного
  run'а. Cache-цена head-варианта записывается в гайд; штатная отрисовка выключена по умолчанию.
