# close() возвращается, пока приём ещё пишет в store

## Зачем

Дефект в **опубликованном** 0.60.0. Проверено чтением:

1. `runtime.ts:420` — `if (admissionClosed) throw closedError()` стоит перед
   `store.acceptInputAndAssignRun(...)`.
2. `close()` (`runtime.ts:725`) выставляет `admissionClosed` и сразу зовёт
   `coordinator.close()`.
3. `coordinator.close()` (`coordinator.ts:170`) сливает только то, что уже
   лежит в `lanes`: активные прогоны и очередь. Заявка, находящаяся внутри
   транзакции store, там ещё не появилась.

Отсюда окно:

```
submit проходит проверку → store пишет → close() → coordinator.close() → settled: true, remaining: 0
                                     → store закоммитил queued run
                                     → coordinator.submit() → "coordinator is closed"
```

Durable-прогон создан, исполнителя у него нет, а вызвавшему сказали, что
сессия закрылась чисто и не осталось ничего. Это ровно тот исход, ради
предотвращения которого close() и писался.

То же окно есть в `resume()` между `loadSnapshot` и `coordinator.submit`, в
recovery после durable `requeue` и вокруг `resolveContext`.

Прежняя таска `close-shuts-admission.md` закрыта с завышенным acceptance: её
тест проверяет close **во время preflight**, то есть до durable-записи, и
поэтому не видит ни одного из этих переходов.

## Результат

- `close()` не возвращает результат, пока каждая уже начатая заявка не
  завершилась одним из двух способов: отказалась **до** durable-записи либо
  передала работу координатору.
- Число не переданных к моменту force-бюджета попадает в `remaining`, а не
  теряется: контракт «результат говорит, на какую сторону сделки ты попал»
  остаётся верным.
- Регрессия ставится на переход, а не на тайминг: детерминированный харнесс
  (`agent-runtime-race.test.ts`) закрывает сессию **внутри** транзакции store
  и внутри handoff'а, а не внутри preflight.

## Что сделано

Окно подтверждено чтением и закрыто барьером.

- [x] `runtime.ts`: `admissionsInFlight` — заявка входит в него сразу после
      проверки закрытия и выходит на отказе **до** durable-записи либо после
      `coordinator.submit`. Никогда не держится на время прогона.
- [x] `close()` ждёт барьер и только потом закрывает координатор. Потраченное
      время **вычитается** из бюджетов координатора, а не прибавляется к ним:
      «любая комбинация ограничена» переживает добавленное ожидание.
- [x] Заявка, не успевшая передать работу в пределах `forceTimeoutMs`, попадает
      в `remaining`, а результат перестаёт быть `settled`.
- [x] Тот же барьер накрывает `resume()` — а через него и восстановление.
- [x] Побочно: `ticket.accepted` координатора теперь наблюдается. В обычном
      прогоне он резолвится, а на отказе после исчерпанного бюджета становился
      unhandled rejection.
- [x] Регрессии: `agent-runtime-close-admission.test.ts` — закрытие **внутри**
      durable-записи и заявка, не успевшая передать работу. Обе проверены на
      убийство: с отключённым барьером падают, с ним проходят.
- [x] `done/2026-08-25-close-shuts-admission.md` дополнен поправкой: его
      acceptance был шире его теста.
