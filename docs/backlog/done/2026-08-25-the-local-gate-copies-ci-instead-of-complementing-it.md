# Обсудить — локальный гейт копирует CI вместо того, чтобы его дополнять

## Зачем

Это предложение спорит с записанной договорённостью (`AGENTS.md`: перед пушем
прогоняется полный гейт), поэтому вынесено на решение владельца, а не сделано.

Измеренное на релизе 0.60.1 / 0.4.1 / 0.4.2:

- Полный матрикс CI: **2 м 23 с**, **2 м 21 с**, **2 м 22 с** — стабильно, потому
  что десять job'ов идут параллельно.
- Тот же набор локально: **7 м 16 с**, **5 м 08 с**, **6 м 34 с** — последовательно.

То есть локальный гейт **медленнее в 2–3 раза того, что он дублирует**, и
занимает 56% времени релиза.

Основной вес — стартовые полосы: target(blank+repository × chromium+webkit) и
head(то же) — восемь прогонов «скаффолд → install → build → playwright». Это
работа, которая по своей природе параллельна и потому принадлежит CI.

Аргумент **за** нынешнюю схему настоящий и его нельзя выкинуть: красный ран на
уже запушенном релизном коммите нельзя починить — по правилу «tag the head»
нужен **новый** релизный коммит. То есть цена красного CI именно на релизном
коммите высокая, и локальный гейт покупает защиту от неё.

Но эта цена относится только к **релизному** коммиту. Для обычного пуша красный
CI стоит две с половиной минуты и ничего больше.

## Результат

Выбрана одна из позиций, и она записана в `AGENTS.md` рядом с правилом, которое
меняет:

- **A.** Оставить как есть. Тогда рычаг — только кеш по хешу дерева (соседняя
  задача), и 19 минут превращаются примерно в 12.
- **B.** Локальный гейт = `lint` + `check` + `test` + дешёвые метаданные
  (~40 секунд), полосы отдаются CI. Полный гейт остаётся обязательным перед
  **релизным** коммитом и только перед ним.
- **C.** Как B, но релизный коммит не пушится напрямую: он проходит через ветку,
  где красный ран ничего не стоит, и попадает в master уже зелёным.

## Что сделано

### Решение
- [x] Принят **вариант B**. Основание: CI фактически надмножество `verify`
      (core-job = lint/check/test/agent-store/build/smokes/consumer-lane,
      starter-матрица = обе полосы во всех вариантах и браузерах, плюс
      supervised) — проверено чтением `.github/workflows/ci.yml`, а не по памяти.
      Дублировать надмножество последовательно на одной машине — не осторожность,
      а более медленная копия.
- [x] Граница проведена не по «доверию к CI», а по цене красного рана на
      конкретном коммите: для обычного — один дополнительный пуш; для релизного
      — целый новый релизный коммит, потому что `assert-subject` + `assert-head`
      требуют, чтобы тег стоял на `release(...)`-голове.

### Code
- [x] `localGateProfile(plan, pushesReleaseCommit)` в `scripts/release-plan.ts` —
      чистая функция: `none` / `fast` / `full`.
- [x] `pre-push`: обычный пуш → `verify.ts --fast --if-changed` (~39 с);
      пуш с релизным коммитом → полный `verify` + packed HEAD, обе с мемо;
      только тег → метаданные релиза, включая новую проверку lockfile.
- [x] `scripts/gate-parity.test.ts` — читает `ci.yml` и держит утверждение
      «CI — надмножество» механически: шаг, добавленный в `VERIFY_STEPS` и не
      добавленный в CI, роняет тест (фальсифицировано).

### Docs

      «before a release commit», добавлен раздел «What runs where» с таблицей

- [x] В дереве нет двух разных утверждений о том, что делает `pre-push`.
