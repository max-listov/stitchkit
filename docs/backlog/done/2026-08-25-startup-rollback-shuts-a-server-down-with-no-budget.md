# Откат неудачного старта останавливает сервер с нулевым бюджетом

## Зачем

Когда старт приложения падает, ядро откатывает уже поднятые ресурсы через
`closeAttempted`, и вызывает `close(contextFor(record, { signal }))` **без**
`deadlineAt` и без `forceDeadlineAt`. Для `managedServerResource` это значит
`now - now === 0` для обоих бюджетов, то есть `shutdown({ gracePeriodMs: 0,
forceTimeoutMs: 0 })` — немедленный жёсткий обрыв запросов, которые сервер уже
принял.

Само по себе это предшествует текущей пачке правок: `Math.max(0, 0)` давал ноль
и раньше. Изменилось другое — **достижимость**. Теперь required-ресурс,
сообщивший о своём здоровье что угодно кроме `healthy`, честно роняет старт, и
откат стал обычным путём, а не редким.

Отдельно стоит заметить, что для force-бюджета ноль — не «маленький бюджет», а
невозможный: сервер выполняет `withTimeout(forceStop(), forceTimeoutMs)` и
падает с «forced shutdown did not complete within 0ms». В самом адаптере это
уже учтено округлением вверх, но здесь ноль приходит не из округления, а из
отсутствия дедлайнов вообще.

## Результат

- Откат неудачного старта останавливает сервер с осмысленным бюджетом, а не с
  нулевым, — либо этот выбор записан как намеренный, с причиной.
- Решение принимается один раз и в одном месте: либо ядро даёт откату дедлайны,
  либо адаптер трактует их отсутствие как «бюджета нет, но и спешки нет».

## План

- [x] Решить, чей это дефолт: у отката нет дедлайна по построению, поэтому
      ноль — это ответ ядра, а не адаптера.
      **Решение: обоих, и это оказались два разных дефекта.** Ядро не давало
      дедлайнов, потому что их некому было передать — откат происходит внутри
      `start()`, у него нет call site. Адаптер трактовал отсутствие как
      «бюджет истёк». Первое чинится объявленным бюджетом на приложении,
      второе — тем, что адаптер молчит и отдаёт дефолты схеме, которая ими
      владеет.
- [x] Проверить, что выбранное поведение не удлиняет откат неограниченно:
      падение старта не должно превращаться в зависание.
      **Проверено пробником, и первый ответ был неверным.** «Ограничено 35 с,
      значит нормально» — это ответ про сервер. Но цикл отката не оборачивал
      `close` ни во что, поэтому ресурс с зависшим `close` держал откат
      **бесконечно** — ровно то зависание, про которое пункт и написан.
      Бюджет теперь не только выдаётся, но и сторожится таймером.
- [x] Покрыть тестом: старт падает при живом сервере с запросом в полёте.
      Настоящий сервер, настоящий запрос, а не двойник.

## Что сделано

### Ядро (`packages/core/src/application/kernel.ts`)

- [x] `ApplicationShutdownBudgetSchema` / `ApplicationShutdownBudget` и поле
      `ApplicationConfig.shutdown` — бюджет объявляется один раз на приложении.
      У отката нет call site, поэтому передать ему опции неоткуда; то же поле
      стало дефолтом для `shutdown()` без опций, чтобы «сколько приложению
      можно останавливаться» было одним числом, а не двумя расходящимися.
- [x] `closeAttempted` тратит объявленный бюджет вместо отсутствующего.
- [x] Бюджет **сторожится**: цикл `close` вынесен в `closeEachAttempted`,
      обёрнут в `untilDeadline` под таймером на force-дедлайне. Незавершённый
      `close` бросается, репортится как отказ фазы `close`, а причина падения
      старта остаётся `cause` у `AggregateError`.
- [x] `shutdown()` мержит опции вызова поверх объявленного бюджета по полям.

### Адаптер (`packages/core/src/application/server-resource.ts`)

- [x] Отсутствующий дедлайн больше не сворачивается в `now`. Поле опускается,
      и дефолты применяет `ShutdownOptionsSchema`, который ими владеет. Это
      чинит класс дефекта, а не одну его расстановку: контекст без дедлайнов
      законно строит conformance kit и может построить потребитель.

### Тесты (`packages/core/tests/application-reported-health.test.ts`)

- [x] `rolling back a failed startup is a shutdown, not an abort` — настоящий
      сервер, настоящий запрос в полёте: запрос отвечает `200`, `start()`
      отвергается **обычной** `Error` с исходной причиной (не `AggregateError`),
      откат укладывается заметно быстрее потолка.
- [x] `a rollback is bounded even when a resource never finishes closing` —
      ресурс с зависшим `close`; проверяет и границу, и сохранение причины.
- [x] `the declared budget is what the rollback spends`.
- [x] `an absent deadline is not a spent one`.
- [x] Все четыре фальсифицированы обратной правкой: без `untilDeadline` первый
      висит до таймаута теста, с захардкоженными дефолтами и с возвратом

- [x] Нулевой бюджет стоил не одного, а трёх вещей. Кроме обрыва запроса

      отказ **подменял диагноз**: `start()` отвергался `AggregateError` с
      текстом про «startup and rollback failed», а сломавшийся ресурс уходил
      строкой ниже. Замерено: обрыв на 39 мс, причина погребена.
