## Зачем

Три независимо поддерживаемых consuming project содержат один и тот же файл —
`error-utils.ts`, 69 строк. Две копии **совпадают побайтово**, кроме одного
`catch`-блока; третья, самая ранняя, несёт в шапке строку
`LIBRARY FILE: no project-specific imports`. Автор знал, что пишет библиотеку, и
ему некуда было её положить.

Что делает файл:

- превращает отказ провайдера в безопасную фразу для конечного пользователя —
  `402` / `insufficient credits`, `429` / `rate limit`, `404` / `no endpoints
  found` — каждая в свою, не в общую «внутреннюю ошибку»;
- распознаёт ошибку, спрятанную **внутри успешного** tool-результата
  (`{ error: … }` и обёртку `{ value: { error: … } }`), потому что провайдер
  вернул 200, а работа не сделана.

Сегодня рантайм даёт `provider_failure` и провайдерский конверт — и не
классифицирует ничего: слов `402`, `429`, `rate limit` в нём нет вовсе. Каждый
потребитель выводит таксономию заново, из наблюдений за своим трафиком, и
расходится с соседом на мелочах, которые видно только в проде.

Это **не доменная модель** (→ ADR 0002): «провайдер сказал 402» — факт о
провайдере, не о предметной области приложения. Владелец этого знания —
`stitchkit/agent-runtime`.

## Результат

- Провайдер-нейтральная классификация отказа: из брошенного значения выводится
  типизированная причина (`insufficient-credits`, `rate-limited`,
  `model-unavailable`, `context-overflow`, `timeout`, `unknown`) с сохранением
  исходного конверта для лога.
- Классификация — **факт, а не текст**: формулировку для пользователя выбирает
  приложение, потому что тон и язык принадлежат ему. Ядро не изобретает фраз.
- Распознавание отказа внутри успешного tool-результата: одна функция вместо
  трёх копий, с тем же разбором обёрток.
- Ничего не меняется в том, что уходит наружу по умолчанию: причина остаётся
  внутренней, если приложение само не решит её показать.

## Acceptance

- [x] Отказ провайдера с 402 классифицируется как `insufficient-credits`, с 429 —
      как `rate-limited`; неизвестный остаётся `unknown` и не выдумывает причину.
- [x] Успешный tool-результат с `{ error }` и с `{ value: { error } }` опознаётся;
      обычный успешный результат — нет.
- [x] Классификация доступна потребителю, который НЕ использует agent-runtime, —
      иначе три копии останутся на месте.
- [x] Исходный конверт провайдера не теряется и не уезжает наружу сам по себе.

## Что сделано

- [x] `packages/core/src/agent-runtime/provider-failure.ts`: `classifyProviderFailure` даёт
      причину, статус провайдера, `retryable` и — то, чего не было в исходных копиях —
      **`evidence`**: статус это ответ провайдера о себе, message-совпадение это наше чтение его
      прозы, `none` это честный отказ гадать. Вызывающий, решающий retry автоматически, обязан
      знать, что из трёх ему досталось.
- [x] Ядро классифицирует и **не формулирует**: фраза для пользователя остаётся приложению.
- [x] `isToolResultFailure` покрывает вторую половину скопированного файла — отказ внутри
      УСПЕШНОГО tool-результата, обе обёртки.
- [x] Обе функции — обычные, без рантайма: копировал этот файл ровно тот потребитель, который
