# S3 — одна декларация проекта вместо рукописного деплойного контура

## Зачем

Деплойный контур шаблона — три файла: `app.config.json`,
`ecosystem.config.cjs`, `ecosystem.dev.config.cjs`.

Исходная формулировка задачи утверждала, что два из них производные и «руками
там ничего не живёт». Против кода это неверно, и неверность существенна:
`ecosystem.config.cjs` читает идентичность и `.env`, но **сам целиком написан
руками** и несёт то, чего нет больше нигде — `script: 'dist/index.js'` против
`script: 'src/index.ts'`, `interpreter_args: '--watch'`, `autorestart: true`,
`kill_timeout: 15000` против `10000`, форму запуска веб-роли через
`node_modules/.bin/next` с портом в `args`. Это не производный файл, а второй
источник правды о том, чем является проект.

Уточнение по абсолютным путям: их там нет. `cwd: path.join(__dirname, ...)`
(`ecosystem.config.cjs:12`) — путь, вычисляемый относительно самого файла в
момент запуска. Проблема не в абсолютности, а в **смешении**: в одном файле
соседствуют вещи, истинные про код (роли, команды, форма запуска), и вещи,
истинные только про место (таймауты супервизии, `--hostname`, порт).

Пока они смешаны, один и тот же репозиторий нельзя корректно поднять в двух
местах, и невозможно ответить, одно ли и то же работает в двух местах.

## Результат

Один декларативный файл. Он **поглощает** `app.config.json`, а не встаёт рядом
с ним: `slug`, `name`, `version` и `description` уже читаются
(`packages/backend/src/index.ts:18,23`, `scripts/local-env.ts:24`,
`scripts/dev.ts:44`), и четвёртый файл контура был бы шагом назад.

Ключи:

- `kind` — `library` либо `application`;
- `identity` — `slug`, `name`, `version`, `description` (то, что сегодня
  `app.config.json`); из `slug` выводятся имена процессов и имя базы;
- `roles[]` — на каждую роль: имя, команды на режимы, признак наличия
  HTTP-входа и **как приезжает порт** (стадия S4 определяет форму);
- `readiness` — **на роль, а не на приложение**: у шаблона две HTTP-роли,
  и у веб-роли сегодня отдельной проверки готовности нет вовсе, тогда как у
  API есть `/health` (`packages/backend/src/index.ts:38-42`). Ключ обязан
  допускать «у этой роли готовность — успешный ответ на корне» и «у этой роли
  слушателя нет вовсе»;
- `build` — команда и что считается артефактом. Артефакт **не один путь**: у
  шаблона это `packages/backend/dist` и `packages/frontend/.next`, а ещё
  `packages/db/src/generated/`, который в `.gitignore` (`_gitignore:9`) и
  порождается `db:generate` до сборки. Ключ обязан описывать множество;
- `requires` — требования рантайма как требования, с порядком относительно
  старта;
- `release` — **что должно произойти до старта ролей, объявленное как факт,
  а не как строка команды**. Понятия не было в исходных шести ключах, а в
  репозитории оно есть: `"pm2:prod": "bun run db:deploy && ... && pm2 startOrReload ..."`
  (`package.json`). Миграция базы — не роль и не требование: она выполняется
  один раз за release, а не при каждом старте процесса.
  Форма — **типизированная**. Ключ объявляет, *что является миграцией*: движок,
  корень миграций относительно commit'а и файл блокировки — у шаблона это
  `packages/db/migrations`, `migration_lock.toml` и `schema.prisma`. Точные
  байты, вердикт допуска и решение пропустить преflight при доказанном
  отсутствии влияния на базу принимает сторона места, читая объявленный корень.
  Репозиторий не диктует ей команду и ничего не знает про режим обслуживания —
  свободный список команд обошёл бы ровно ту типизацию, ради которой ключ и
  нужен.
  `ensure-built` (`packages/backend/scripts/ensure-built.ts`) в этот ключ **не
  входит**: это преflight сборки, и его место в `build`;
- `env.required[]` — только имена и форма значения, без значений (S7 отвечает
  за то, чтобы это не стало третьей копией схемы окружения).

**Граница — одно правило, по которому проверяется всё остальное:**

> Файл обязан быть осмысленным и полным, **когда не существует ни одной ноды**.
> Если поле нельзя заполнить, не зная, где оно поедет, — это binding, а не
> декларация.

Из него следует, что внутрь не попадает никогда:

1. Любое значение, различающееся между двумя deployment'ами: домен, хост,
   абсолютный URL, номер порта, строка подключения к базе, TLS. Имя
   переменной — можно, значение — никогда.
2. Любой путь на машине.
3. Форма маршрутизации наружу. Репозиторий говорит «этой роли нужен
   HTTP-вход», а не как он выставлен.
4. Политика супервизии: перезапуск, число инстансов, лимиты. **Кроме одного
   исключения** — минимальное время слива, которое является свойством кода;
   его границу задаёт стадия S5.
5. Секреты, включая имена, подразумевающие конкретное хранилище.
6. Версия или свойства самой платформы. Иначе её обновление становится правкой
   в каждом репозитории-потребителе — то есть форком, а не зависимостью.
7. Всё выводимое из уже объявленного: повторить руками значит завести второй
   источник правды.

## Что сделано

### Схема (ядро)

- [x] `ProjectDeclarationSchema` расширена до полной декларации: `kind`,
      `identity`, `roles`, `build`, `requires`, `release`, `env`.
- [x] **Граница держится формой, а не ревью.** В схеме физически негде разместить
      порт, хост, абсолютный URL, путь машины, правило маршрутизации или политику
      супервизии: `BindingVariableSchema` принимает только ИМЯ переменной,
      `RepositoryPathSchema` отвергает абсолютный путь и `..`, команда с `://`
      отвергается, а `kind: library` не может иметь ролей.
- [x] `readiness` — на роль, а не на приложение; `listener` необязателен, и его
      отсутствие означает «у роли нет слушателя вовсе», а не «декларация неполна».
- [x] `build.artifacts` — множество путей: у шаблона их три, включая
      порождаемый gitignored `packages/db/src/generated`.
- [x] `release.migrations` — **байты, а не команда**: движок, корень и файл
      блокировки. Вердикт допуска остаётся у стороны, которая видит deployment.
- [x] `requires` несёт `phases`, а не дублируется по имени.
