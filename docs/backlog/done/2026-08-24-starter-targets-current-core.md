# A freshly scaffolded project starts on the current core

## Зачем

`packages/create-stitchkit/template/package.json` объявляет
`catalog.stitchkit: "^0.52.0"`, опубликованный scaffolder — `0.3.3`. Ядро при
этом на 0.59.x. Между целью шаблона и текущим ядром семь миноров, из которых
шесть несут breaking-секции.

Практическое следствие: проект, созданный сегодня, стартует без всего, что
появилось с 0.53 — нейтральной отмены клиентских запросов, managed-файлов,
композиции auth-доменов, асинхронных операций, политики представления CLI,
агент-рантайма и ядра приложения. Через некоторое время этому проекту
понадобится сквозная миграция через шесть breaking-релизов вместо ни одного.

Шаблон при этом **не сломан**: HEAD-лейн, ставший fail-closed после ADR 0099,
зелёный на текущем ядре, то есть шаблон компилируется и работает против HEAD.
Отставание — в цели target-лейна, а не в совместимости.

Отдельная причина не тянуть: витрина фреймворка показывает состояние недельной
давности, и первое впечатление о проекте формируется по ней.

## Результат

- `catalog.stitchkit` шаблона указывает на актуальную опубликованную версию
  ядра.
- Шаблон использует те возможности новых версий, которые уместны в стартовом
  приложении, и не тянет в него слои, которым там не место.
- Оба лейна — target и head — зелёные на новой цели.
- Scaffolder выпущен своим тегом; версия ядра при этом не двигается.

## План

- [x] Прочитать `### ⚠️ Breaking changes` в `CHANGELOG.md` для каждой версии от
      0.53.0 до актуальной и применить к шаблону всё, что его касается.
      Опираться на changelog, а не на `docs/guide/upgrading.md`: разделы
      миграции для 0.57.0–0.59.0 там появятся только вместе с отдельной задачей
      про гейт upgrade-гайда, и ждать её не нужно.
- [x] Поднять `catalog.stitchkit` до `^0.59.0` — каретный диапазон на минор, как
      и текущий `^0.52.0`, а не патч-точная версия — и обновить lockfile.
- [x] Зафиксировать в шаблоне текущее положение: `agent-runtime` и
      `application` в него **не** входят — стартер демонстрирует контракт, HTTP,
      клиент, CLI и observability, а не всю поверхность. Это уже факт (шаблон
      импортирует только `stitchkit`, `/contract`, `/server`, `/tools`, `/cli`,
      `/observability`); задача его подтверждает, а не открывает заново.
      Изменение этого решения требует отдельного обоснования.
- [x] Прогнать `bun run starter-lane` и `bun run starter-head-lane`, оба
      варианта и все браузеры.
- [x] Обновить `packages/create-stitchkit/CHANGELOG.md`.
- [x] Выпустить scaffolder по штатному flow: бамп только его `package.json`,
      его собственный changelog, зелёный прогон, тег `create-stitchkit-vX.Y.Z`.

## Acceptance

- [x] `catalog.stitchkit` равен `^0.59.0`, и версия из этого диапазона уже
      существует на npm.
- [x] `bun run starter-lane` и `bun run starter-head-lane` зелёные во всех
      вариантах и браузерах — это и есть доказательство, что свежесозданный
      проект поднимается без ручных правок.
- [x] Версия ядра не изменена: релиз шаблона не двигает и не публикует ядро.
- [x] Тег scaffolder указывает на релизный коммит с зелёным прогоном.

## Не входит

- Изменения самого ядра. Если при подъёме обнаружится дефект ядра, он
  оформляется отдельной задачей и своим релизом.
- Автоматическое отслеживание цели шаблона за каждым релизом ядра: политика
  пропуска HEAD-лейна и порядок подъёма цели уже описаны в ADR 0099, и эта
  задача её не меняет.
- Ожидание релиза 0.60.0: если задача про единый словарь shutdown выйдет
  breaking-минором раньше, шаблон отстанет на один минор и будет поднят
  следующим проходом. Держать стартер незапущенным ради этого не нужно.
