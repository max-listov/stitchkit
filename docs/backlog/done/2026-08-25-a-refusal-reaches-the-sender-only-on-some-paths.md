# Отказ доходит до отправителя не на всех путях, где мог бы

## Зачем

ADR 0106 называет ровно две границы, за которыми отказ остаётся локальным:
fire-and-forget событие и событие, которого нет в контракте получателя. Ревью
нашло, что границ больше, а один из потолков существует только на бумаге.

**Третий разрыв версий, и он самый обычный.** `splitWireArguments` вынимает
колбэк подтверждения только когда `definition.ack` есть у **получателя**.
Если получатель на старой версии контракта, где у события ещё нет `ack`, а
отправитель на новой уже передаёт колбэк, — колбэк физически лежит в кадре, но
код на него не смотрит: он попадает в `values`, разбор аргументов падает по
арности, и `answerWithRejection` получает `undefined`. Отправитель ждёт дедлайн
и рапортует таймаут — ровно тот отказ, ради устранения которого всё делалось.
Подтверждено пробником. Добавление подтверждения к существующему событию —
нормальная эволюция контракта, и примерно в половине случаев она выкатывается
отправителем вперёд.

**Потолок issues есть только на читающей стороне.** `MAX_ISSUES = 20`
используется в `parseIssues`, то есть при разборе входящего конверта.
Производящая сторона зовёт `zodIssues(parsed.error)` без ограничения.
Подтверждено: событие с массивом из 50 плохих элементов породило конверт с 50
issues на проводе. Комментарий в коде и ADR утверждают обратное; рядом в
`internal/errors.ts` уже лежит `MAX_DETAIL_ISSUES = 20` ровно для этого.
Размер ответа управляется входом отправителя — это усиление на сокете.

**Причина отказа не переживёт собственную эволюцию.** `asRealtimeRejection`
жёстко отвергает любую `reason`, кроме `invalid-arguments`, и возвращает `null`.
Тип при этом задокументирован как «union из одного, и намеренно union». Когда
следующая версия добавит вторую причину, пир на текущей версии получит `null`,
конверт уйдёт в ack-схему приложения, и отправитель увидит
`RealtimeRequestInvalidAcknowledgementError` — ту самую характеристику «пир
ответил чем-то невалидным», которую комментарий рядом обещает не выдавать.
Механизм версионирования, который сам не версионируется вперёд.

**`emit(..., callback)` половину обещания не выполняет.** На отказ хук
`onRejected` срабатывает, а колбэк приложения не вызывается никогда
(подтверждено). `request()` бросает типизированную ошибку; `emit` с колбэком
получает тишину плюс боковой канал. Приложение, повесившее свой дедлайн на
колбэк, по-прежнему видит таймаут. Это согласуется с уже существовавшей веткой
`invalid-acknowledgement-value`, то есть, возможно, так и задумано, — но
заголовок «отказ, который видит отправитель» на этом пути выполнен наполовину,
и нигде об этом не сказано.

**И одно последствие, не разобранное в ADR.** Получатель теперь вызывает
колбэк, который раньше на отказном кадре не вызывался никогда. Для пира на
stitchkit это разобрано. Для обычного socket.io-клиента или любого не-stitchkit
отправителя — нет: его колбэк начинает выполняться на пути, на котором раньше
не выполнялся.

## Результат

- Колбэк извлекается для ответа независимо от того, есть ли `ack` у контракта
  получателя, — отказ доходит и при выкатке отправителем вперёд.
- Потолок issues действует там, где конверт **создаётся**, а не только там, где
  он читается; комментарий и ADR соответствуют коду.
- Неизвестная будущая причина отказа читается как отказ, а не деградирует в
  «пир ответил невалидным».
- Про путь `emit(..., callback)` сказано прямо: что происходит и почему.
- ADR 0106 перечисляет все границы, а не две из них, и называет последствие для
  не-stitchkit отправителя.

## План

- [x] `splitWireArguments`: извлекать хвостовой колбэк всегда, но использовать
      его только для ответа отказом — доставку в обработчик оставить как есть.
- [x] Ограничить issues при создании конверта; переиспользовать существующую
      константу вместо второй такой же.
- [x] `asRealtimeRejection`: принимать любую непустую строковую причину,
      неизвестную нормализовать; расширить тип на проводе честно.
- [x] Дописать ADR 0106: третий разрыв, путь `emit`, последствие для
      постороннего отправителя.

## Acceptance

- [x] Тест: получатель без `ack` в своём контракте отвечает отказом отправителю,
      который колбэк передал.
- [x] Тест: конверт, созданный из ошибки с 50 issues, несёт не больше потолка.
- [x] Тест: конверт с неизвестной причиной опознаётся как отказ.
- [x] `bun run verify` зелёный.

## Что сделано

### Core
- [x] `splitWireArguments` возвращает `replyTo` — колбэк, который физически на
      проводе, независимо от того, знает ли о нём контракт получателя. Отказ
      уходит через него, поэтому выкатка отправителем вперёд получает отказ, а
      не таймаут. `values` намеренно не тронуты: кадр и так отвергается, а тихо
      переинтерпретировать список аргументов ради уже отвергаемого случая —
      менять то, что видят обработчики.
- [x] Потолок issues применяется там, где конверт **создаётся**
      (`MAX_REJECTION_ISSUES`), а не только при чтении.
- [x] `reason` на проводе — строка, а не закрытый union: причина из будущего
      релиза читается как отказ, а не деградирует в «пир ответил невалидным».

### Tests
- [x] `realtime-rejection-visibility.test.ts` — 9 тестов. Два бывших
      тавтологичных заменены наблюдением **реального провода** через
      contract-blind клиент: что именно получает старый пир, видно, а не
      сконструировано. Новые: выкатка отправителем вперёд отвечена, потолок
      действует при отправке, неизвестная причина опознана.
- [x] Фальсифицировано по отдельности: возврат к `acknowledgement` роняет тест
      про выкатку вперёд (таймаут 5 с); снятие потолка роняет тест про потолок.
      Первая версия теста про потолок **не могла упасть** — читающая сторона
      тоже режет до 20; исправлено чтением сырого конверта.

### Docs
- [x] ADR 0106: третий разрыв, строковая причина, потолок при создании, путь
      `emit(..., callback)` (отказ идёт в `onRejected`, колбэк не вызывается) и
      последствие для не-stitchkit отправителя, чей колбэк теперь срабатывает
      там, где раньше не срабатывал. CHANGELOG приведён в соответствие.
