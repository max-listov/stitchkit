# Тест коалесцирования недетерминирован в CI

## Зачем

При релизе стартера 0.4.0 job `Framework, Node and publication artifacts`
(run `32798512064`, коммит `e561f2c`) упал на одном тесте:

```
packages/core/tests/agent-runtime-terminal.test.ts:222
agent runtime terminalization > coalesces inputs behind an active run into one durable successor
expect(received).toHaveLength(expected)   Expected: 2   Received: 1
```

Коммит трогал только файлы стартера, `AGENTS.md`, `package.json` и полосы — к
agent-runtime он отношения не имеет. Повтор того же job на том же SHA прошёл;
локально не воспроизводится: десять последовательных прогонов файла, три полных
прогона набора ядра и восемь параллельных прогонов — все чистые.

Строка 222 — это `expect(queued.runs).toHaveLength(2)`: активный прогон плюс
успешник. Предшествующие утверждения в том же тесте прошли, то есть обе заявки
получили один и тот же `runId` и возрастающие `snapshotVersion`. При этом
снимок показал один прогон. Прочитанное объяснение не найдено: `accepted`
резолвится **после** записи в store (`runtime.ts:501`, после двух publish), а
memory-драйвер сериализует транзакции через `transactionTail`.

Почему это нельзя оставить: тест сторожит terminal CAS и коалесцирование —
именно ту гонку, ради которой он написан. Недетерминированный сторож не отличим
от сломанного: следующий такой отказ спишут на флейк, и настоящий регресс
проедет.

## Результат

- Причина названа: либо тест наблюдает состояние в момент, когда оно ещё
  законно не установилось (тогда чинится наблюдение), либо в рантайме есть
  окно, в котором успешник не виден после разрешённого `accepted` (тогда
  чинится рантайм).
- Тест либо детерминирован, либо заменён на детерминированную проверку того же
  свойства.
- Если причина в рантайме — регрессия ставится на неё, а не на тайминг.

## Что сделано

### Воспроизведение

«Не воспроизводится» держалось на форме прогона, а не на редкости. Отказ
воспроизвёлся с первой попытки, как только прогон повторил условия runner'а:
два ядра (`taskset -c 0,1`) плюс четыре занятых процесса на тех же ядрах,
`bun test --rerun-each=120`. **33 падения на 1800 тестов**, все — одна и та же
строка. Гипотеза «редкая гонка» была неверна: на разгруженной 12-ядерной машине
условие просто не наступало.

### Причина

Падала не та строка, которую называла эта таска. `:222` — это не
`expect(queued.runs).toHaveLength(2)` (она проходила), а
`expect(queued.runs[1]?.inputMessageIds).toHaveLength(2)`. Снятый снимок в
момент отказа:

```
runs[0] = { state: 'queued',  inputs: [input-2, input-3] }   ← преемник
runs[1] = { state: 'running', inputs: [input-1] }            ← активный
```

Коалесцирование сработало ровно так, как задумано: оба ввода в одном
преемнике, один `runId`, растущий `snapshotVersion`. **Рантайм ни в чём не
виноват.** Виновата позиция: `snapshotOf` сортировал прогоны по
`(createdAt, id)`, а преемник за активным прогоном создаётся в ту же
миллисекунду — ISO-отметка их не разделяет, и ничья уходила на случайный UUID.
Примерно в половине совпадений по миллисекунде `runs[1]` оказывался активным
прогоном, а не преемником.

- [x] Ядро: `packages/core/src/agent-runtime/store-driver.ts` —
      `historyPositions()` и второй ключ сортировки в `snapshotOf`. При
      совпадении `createdAt` порядок решает позиция самого раннего сообщения
      прогона в истории: она причинна, её каждый драйвер и так держит (на ней
      стоит компакция и построение prompt'а), и она не зависит от драйвера.
- [x] Ядро: `packages/core/src/agent-runtime/schemas.ts` — порядок `runs`

- [x] Тест: `packages/core/tests/agent-runtime-terminal.test.ts` — преемник
      адресуется по личности (`find` по `runId`), а порядок проверяется
      отдельным утверждением. Тест, которому нужно свойство коалесцирования, не
      должен зависеть от порядка вовсе.
- [x] Регрессия: `packages/core/tests/agent-runtime-store.test.ts::orders runs

### Чего это стоило понять

Прошлый заход записал сюда «повтор job'а прошёл, локально не воспроизводится» и
на этом остановился — но десять последовательных прогонов на свободной машине
не опровергают гонку, они её не вызывают. Опровергающий пробник должен был
воспроизводить не количество прогонов, а **дефицит ядер**. И вторая ошибка
дешевле первой: номер строки в отчёте CI был записан, но не сверен с файлом —
из-за чего таска полтора абзаца рассуждала не о том утверждении.
